2. Purpose, actors, and component boundaries


The project combines network intrusion detection with human-directed subscriber security management. It collects MikroTik NetFlow export records, associates observed addresses with PPPoE subscriber names, computes numerical traffic features, sends those features to a two-stage classifier, stores classifications in MySQL, and presents the results through a Laravel website. An administrator can request blocking or restoration; a local router-facing reconciliation agent implements those requests. Detection alone does not automatically block a subscriber in the current main path.

The monitored subscriber generates network traffic through the MikroTik gateway. The gateway exports NetFlow records and exposes active PPP sessions and firewall management through the RouterOS API. The local monitoring computer receives those records, performs feature aggregation, runs or contacts the detector, and reaches the database and router. Hostinger hosts the Laravel website and the shared MySQL database. A browser displays database-derived dashboards and submits administrator actions. The database is the coordination point between detection, presentation, and enforcement.

The administrator has read access plus threat management permissions. The viewer account has read access to protected pages and read endpoints, including report export, but cannot submit threat changes. The detector is a machine client of the model service and a database writer. The blocker/restorer is a database reader and router controller. These machine processes do not authenticate as the website viewer; website session restrictions do not automatically secure their separate network interfaces.

The principal local scripts are setup/Mikrotek PPPoe Sniffer.py, setup/Detection Process.py, and setup/Pending Blocker.py. The historical spelling Mikrotek is part of the filename. The first script is a NetFlow collector rather than a raw packet sniffer. The second hosts a Flask inference API and writes classifications directly to MySQL. The third performs both blocking and restoration. No separate current Restorer.py service is required or present in the inspected main setup.

Laravel follows a route, middleware, controller, model, and Blade view structure. Routes select controllers; CheckSession validates the custom session and role; controllers query or update Eloquent models; Blade templates render HTML; browser JavaScript polls selected endpoints. Database migrations define persistent storage. Composer manages PHP dependencies; npm and Vite manage the source asset build; most visible administration pages also load prebuilt static template assets directly from public/admin.


3. End-to-end system flow and timing


Step one: configure MikroTik to export NetFlow version five records to the monitoring computer on UDP port 2055 and make RouterOS API access available to that computer. The repository contains router inspection and removal notes but does not automatically configure Traffic Flow export. The collector binds an IPv4 UDP socket on all local interfaces and accepts packets only when the sender address equals the configured MikroTik host.

Step two: query active PPP sessions through the RouterOS API. The collector builds a mapping from each current subscriber address to its stable PPPoE username, filters excluded address prefixes, and adds recognized addresses to a round-robin queue. A current address is an observation, not the long-term subscriber identity. The queue is refreshed using active session data, and addresses absent from a successful refreshed mapping are removed from queue state.

Step three: parse each supported NetFlow packet. Version five uses a 24-byte header followed by 48-byte records. Extract source and destination IPv4 addresses, source and destination ports, packet count, byte count, first and last flow timestamps, TCP flag bits, and protocol number. Record a local collection timestamp. Store each accepted flow in both source-address and destination-address indexes.

Step four: approximately every 60 seconds, select one queued subscriber and gather records where that subscriber appears in either direction. Require at least ten indexed flow records before analysis. Retain at most the most recent 200 outgoing records and 200 incoming records for feature calculation. Refresh subscriber mappings approximately every 300 seconds and remove stored flow records older than one hour during the periodic analysis branch.

The timing checks are inside the successful UDP receive path. A socket timeout immediately continues the loop. Consequently, these are traffic-driven checks, not independent scheduled timers: no incoming export traffic can delay subscriber refresh, analysis, and memory cleanup. A queue with N active clients normally revisits one client in roughly N times 60 seconds, plus processing and traffic delays; it does not analyze every subscriber every 60 seconds.

Step five: submit one JSON request to the configured inference URL, with a 30-second request timeout. The current detector validates presence of all required model features, coerces feature values to finite numeric values, computes Stage A attack probability, applies the configured threshold, and invokes Stage B only when Stage A predicts attack. The response includes the decision, probability, optional attack family, used threshold, and feature accounting information.

Step six: append the classification record to a local JSON-lines prediction log and attempt a database transaction. A benign result creates a detection row without an incident. An attack result either updates an eligible incident or creates a new unresolved incident, then inserts the detection referencing that incident. The website reads the same database and updates selected displays through polling or page navigation.

Step seven: an administrator selects Block. The website updates the chosen incident to blocked, records the request timestamp, and clears restoration and synchronization markers. The browser response confirms the database request, not router completion. Approximately every 20 seconds, the local agent reads all blocked PPPoE subscribers, resolves each current address, and maintains subscriber-owned forward-chain drop rules.

Step eight: an administrator selects Restore. The controller method is historically named ignore, but the operation sets the incident to resolved and records restoration time. The local agent only processes a pending restore when there is no other blocked incident for the same subscriber. It removes subscriber-owned rules, clears tracked connections for relevant addresses, and marks the resolved incident synchronized. The incident and its logs remain as historical evidence.

The website dashboard polls every 15 seconds while the document is visible. The system-status alert fragment also polls every 15 seconds. The live-monitor demonstration updates synthetic chart values every two seconds and timestamps every five seconds; those intervals do not measure the real collector or router. Overall response time combines export timing, queue position, inference time, database availability, browser polling, and enforcement polling.


4. NetFlow collector and subscriber discovery


Source: setup/Mikrotek PPPoe Sniffer.py. MikroTikConnector holds a RouterOS connection pool, API handle, and connection state. connect creates a pool using the configured router host, API port, username, and password. The current code selects no SSL and plaintext login. A failed connection is logged and reported as false. get_pppoe_clients reconnects when necessary, reads /ppp/active, extracts address and name, discards incomplete entries, and returns the accepted address-to-name mapping.

The is_client_ip helper rejects empty addresses, zero and broadcast endpoints, and a literal list of infrastructure-like string prefixes. The list includes the 100.64 through 100.127 carrier-grade address prefixes, selected 190.168 through 193.168 prefixes, loopback, link-local, and several multicast or reserved prefixes. It uses textual starts-with matching rather than a formal subnet library. It should not be described as a complete standards-based IPv4 classification policy. The separate is_infrastructure_ip helper also excludes addresses beginning with 192.168 and selected multicast or reserved prefixes.

NetFlowCollector creates the UDP socket, sets a one-second receive timeout, initializes per-source and per-destination flow lists, initializes the round-robin queue and known-client set, and maintains the current PPPoE mapping. parse_netflow_v5 checks minimum packet length and stops when an advertised record would exceed the available bytes. The main loop checks the NetFlow version before calling it. Versions other than five are ignored; template-based NetFlow version nine and IPFIX are not implemented by this parser.

Flow duration is the exported last timestamp minus the first timestamp in milliseconds. Negative or wrapped exporter counters are not explicitly repaired. The parser excludes a record if either endpoint is considered infrastructure by its filter. This may exclude traffic that an operator expects to monitor, particularly private-address traffic through a gateway. Every surviving record receives a local ISO-format timestamp; the collector does not store packet payloads or reconstruct application content.

update_client_list replaces the address-to-name mapping, prunes addresses absent from the new active set, and queues newly recognized addresses. get_next_client rotates the deque before returning its first element. store_flow indexes one flow under both endpoints, and get_client_flows concatenates both indexes for the selected address. The indexes intentionally support bidirectional observation, but they are not a strict five-tuple conversation reconstruction. Self-addressed records can appear in both indexes.

In the receive loop, subscriber discovery is refreshed only if the router query returns a nonempty mapping. An empty mapping or failed query therefore leaves the prior mapping in place. This is a relevant limitation when every PPP session disconnects or API access fails. The receive buffer is 8192 bytes. Export datagrams larger than that buffer can be truncated, while the parser processes only records that fit in the received buffer.

analyze_next_client consumes the next queue position even when it skips a subscriber with too few records. It builds a payload, logs traffic summaries, and posts it once. There is no persistent outbound queue, request retry loop, duplicate identifier, or delivery acknowledgement tied to a committed database row. Data retained in memory may be re-aggregated on a later turn, so successive classifications are overlapping observations, not necessarily disjoint network sessions.

The collector writes setup/logs/merged_ids.log and console output. MergedIDS obtains an initial PPP client mapping before entering the receive loop. The Windows launcher opens each component in a separate console. Exceptions are printed with a pause-on-error hook where applicable. Stopping the console or losing the monitoring computer stops collection; the hosted website can remain available while its data becomes stale.


5. Traffic features and measurement semantics


The current training contract contains fourteen ordered features under schema version mikrotik-netflow-v1. Feature order is taken from the loaded model bundle during inference, rather than inferred from JSON key order. Source and destination addresses, subscriber identity, ports, protocol, timestamps, TCP-flag counters, and several extra statistics are also transmitted for context, but not all are model inputs or persisted database columns.

destination_port is the latest context record's destination port. flow_duration is the sum of selected flow durations in milliseconds multiplied by one thousand, producing a microsecond representation. It is a sum of exporter durations across selected records, not the wall-clock span between first and last client activity. Concurrent flows can therefore contribute overlapping time.

total_fwd_packets and total_backward_packets are packet totals for outgoing and incoming selected records. total_length_of_fwd_packets and total_length_of_bwd_packets are their byte totals. fwd_packet_length_mean and bwd_packet_length_mean are packet-weighted means derived from each export record's bytes divided by packets. These represent aggregate estimates; NetFlow records do not supply each original packet length.

flow_bytes_s and flow_packets_s divide aggregate bytes and packets by the summed duration converted to seconds. fwd_packets_s and bwd_packets_s use the same denominator for each directional packet count. If aggregate duration is not positive, the code uses one second as a fallback denominator. down_up_ratio is incoming packets divided by the greater of outgoing packets and one. average_packet_size is aggregate bytes divided by the greater of aggregate packets and one.

The collector includes both compact database-friendly keys and normalized training keys. tot_fwd_pkts corresponds to total_fwd_packets; tot_bwd_pkts corresponds to total_backward_packets; tot_fwd_bytes corresponds to total_length_of_fwd_packets; tot_bwd_bytes corresponds to total_length_of_bwd_packets; fwd_pkt_len_mean and bwd_pkt_len_mean correspond to their expanded packet-length feature names; flow_pkts_s corresponds to flow_packets_s; dst_port corresponds to destination_port.

Additional transmitted fwd_iat_mean and bwd_iat_mean are computed by dividing the summed duration in milliseconds by the corresponding directional packet count with a minimum denominator of one. They are not measured packet-by-packet inter-arrival intervals, and they are not part of the fourteen-feature current training contract. syn_count, ack_count, fin_count, and rst_count count selected export records carrying each flag bit, rather than reconstructing the exact number of packets with that flag.

The context record prefers the latest outgoing record and falls back to the latest incoming one. src_ip is always set to the subscriber being analyzed, even when the fallback context record originally had that subscriber as its destination. Thus destination address and port metadata may not describe a canonical subscriber-to-server conversation in the incoming-only case. A classification represents a subscriber aggregate across many records and destinations, not proof that one displayed destination caused the prediction.

Packet-length means are calculated by expanding repeated mean values into lists once per packet. Large exported packet counts can consume substantial memory even though only a few hundred flow records are selected. A weighted-sum calculation would avoid this implementation cost, but this reference records the present behavior without changing it. Training data uses CICFlowMeter-derived columns, while deployment computes aggregate NetFlow approximations; matching column names and units does not alone prove identical statistical distributions.


6. Detector API, persistence, and incident assignment


Source: setup/Detection Process.py. The script loads environment settings from setup/.env, chooses a model filename under setup/data/model, and deserializes a trusted joblib bundle at startup. The default filename is netflow_ids.joblib. Required bundle entries are bin for the binary model, mul for attack-family classification, features for ordered feature names, and best_threshold. An optional schema_version is exposed to clients; missing schema metadata becomes unknown.

IDS_THRESHOLD overrides the bundle threshold and must be within zero and one inclusive. The code trims expected feature names and incoming JSON keys. It maps selected compact sender names into normalized model names when the normalized field is absent. A supplied normalized field takes precedence over its alias. Missing required feature names produce a 422 response containing error missing_model_features, schema_version, missing_expected_features, present_expected_features, and expected_features_count.

For each required feature, conversion to float is attempted. Conversion failures, NaN, and infinity become zero. Therefore feature presence validation is stricter than value validation: a present but malformed value may silently become zero. The API expects an object-like JSON body; request JSON is forced, and there is no dedicated input schema enforcing valid ranges, record size, subscriber identity, or approved source hosts. The source does not configure API authentication or rate limiting.

Stage A calls predict_proba and takes the second probability column as the attack probability. A probability at or above the selected threshold yields risk_level attack; lower values yield benign. Stage B predicts one attack-family string only for an attack. Benign attack_type remains null. The response returns risk_level, prob_attack, attack_type, used_threshold, present_expected_features, missing_expected_features, received_features_count, api_version debug-v3, and schema_version.

The detector constructs a record containing an epoch-second timestamp, the received normalized data, and prediction results. append_log creates the configured log directory and appends a JSON record to predictions.jsonl. Log failures are printed and do not stop database saving. save_to_database constructs a selected column payload, obtains a MySQL connection with autocommit disabled, assigns an incident if appropriate, inserts the detection, and commits. On transactional failure it rolls back and prints an error; the outer inference handler can still return a successful classification response.

A successful inference response is consequently not a durable-storage guarantee. Missing database name or username explicitly skips insertion. Database exceptions are handled internally rather than converted into an HTTP failure. Neither a local prediction-log entry nor a successful collector response proves that Laravel can read a newly committed row. Operators should verify database timestamps or the logs page independently when diagnosing missing observations.

assign_incident returns no incident for non-attack records. For an attack with a PPPoE name, it searches for the same subscriber name and attack type. A blocked incident is eligible without the unresolved time-window restriction and is preferred over unresolved incidents. Otherwise an unresolved incident is eligible only if its last detection falls within INCIDENT_WINDOW_MINUTES, which defaults to fifteen and is clamped to at least one. The selected row is locked for update within the transaction.

An eligible incident increments event_count and updates last_detected_at and updated_at. Otherwise a new incident starts with status unresolved, event_count one, and first/last detection timestamps. Resolved incidents are never reopened by this query. An attack without a PPPoE name creates a new incident rather than reusing an unidentified address group. The new detection is linked through incident_id. The schema does not enforce a uniqueness constraint covering eligible incident identity; row locking does not fully prevent concurrent first-insert races when no matching incident exists.

The script starts Flask on all interfaces, port 5000, with debug enabled when executed directly. This is an implementation fact, not a hardened production deployment recommendation. The API root returns a simple running message; it does not exercise the model prediction path, database transaction, collector, or router. Loading an artifact can fail before the server starts. The bundle is not inspected dynamically by this documentation process because joblib deserialization executes trusted Python object loading behavior.


7. Blocker, restorer, and router reconciliation


Source: setup/Pending Blocker.py. The process loads shared settings, creates setup/logs/blocked_threat_sync.log, connects to RouterOS, and repeatedly polls MySQL. BLOCK_SCAN_INTERVAL defaults to twenty seconds. BLOCK_RULE_PREFIX defaults to IDS block. DB_TABLE defaults to intrusion_logs and DB_INCIDENT_TABLE defaults to threat_incidents. This service must run on a host that can reach both the database and the MikroTik API.

get_blocked_subscribers selects distinct nonempty PPPoE names with at least one blocked incident. It intentionally continues enforcing a blocked subscriber on every scan rather than treating a block as a one-time command. get_pending_restores selects resolved incidents whose firewall_synced_at is null, whose PPPoE name is nonempty, and for which no blocked incident exists for that same name. This prevents restoring one historical incident from overriding another currently blocked incident for the subscriber.

The main loop processes all blocked subscribers before pending restores, isolates individual subscriber failures with logging, catches scan-level errors, and sleeps before the next iteration. Initial ensure_connected occurs before the main loop; a startup router connection failure can terminate startup. Inside the loop, ensure_connected primarily checks whether an API object exists rather than proving an existing session is healthy. There is no general reconnect/backoff supervisor implemented around every transport failure.

Stable rule ownership is encoded as a comment consisting of the configured prefix followed by pppoe and the subscriber name, with a colon between pppoe and the name. The comment is truncated to 255 characters. Matching rules are sought in the forward chain with action drop and this exact ownership comment. These are source-address drop rules, not PPP account deletion, password changes, or a complete bidirectional quarantine policy. Existing firewall rule order and FastTrack behavior remain relevant to effective enforcement.

resolve_current_ip_for_pppoe queries /ppp/active using the supplied name. If no exact response is returned, it reads active sessions and compares trimmed lowercased names. Missing active sessions or missing assigned addresses raise a runtime error rather than falling back to an old detection address. This avoids intentionally using an obsolete observed address to block a different subscriber after dynamic reassignment.

block_subscriber first attempts legacy IP-owned rule cleanup, then resolves the current PPP address. It inspects subscriber-owned rules, removes those targeting obsolete source addresses, and distinguishes enabled and disabled rules for the current address. An enabled current rule is retained. Disabled current rules are re-enabled. If none exists, it creates a forward-chain source-address drop rule. It then clears matching tracked connections. The implementation does not move a newly added rule to a guaranteed position ahead of preexisting accepts or FastTrack rules.

_known_ips_for_pppoe reads distinct historical src_ip values for the name from intrusion_logs. _remove_legacy_subscriber_rules uses these addresses to identify older comments containing the prefix and address. This migrates from IP ownership to subscriber ownership. Historical address reuse means an address-only legacy rule may be ambiguous across subscribers. Cleanup therefore has historical assumptions that should be understood before treating ownership as perfect.

unblock_subscriber removes legacy rules, retrieves all matching subscriber-owned rules, collects their source addresses, and attempts deletion of each identifiable rule. It also resolves the subscriber's current active address when possible, but an offline subscriber does not prevent removal of already known owned rules. It clears tracked connections for collected addresses. The ordinary current restoration path does not require SSH, Paramiko, a PPP session disconnect, or a separate restorer process.

mark_restore_synced writes the current database time into firewall_synced_at only for the selected incident while it remains resolved. However, the current unblock_subscriber path does not assert that all deletion helpers succeeded or re-query owned rules before this marker is written. _remove_firewall_rule returns false after exhausting its fallbacks, and callers do not consistently propagate that result. Accordingly, the synchronization timestamp records that the agent reached that step; it is not an independently verified guarantee that every firewall rule disappeared.

The service retains legacy block_ip and unblock_ip helpers plus direct RouterOS protocol support. RouterOsDirectClient implements variable-length word framing, sentences, socket reads, ordinary login, challenge-response fallback using MD5, and command dispatch with trap detection. _set_firewall_rule_enabled tries several identifier forms through direct API and library fallbacks. _remove_firewall_rule tries identifiers with and without the RouterOS asterisk, different parameter names, direct API removal, and a final command-style fallback. These compatibility methods support different RouterOS API representations.

clear_connections queries source and destination tracked connections and attempts to remove each unique identifier. clear_ppp_active can disconnect PPP sessions by address, but is not invoked by the current subscriber reconciliation flow. Old variable names such as dst_ip in legacy blocking methods refer to the address being blocked even though the created filter matches source address. Function names should not be used to infer destination-based blocking policy.

The browser may display blocked or resolved before the router reaches that state. Blocking is continuously reconciled, while restoration is treated as pending until the synchronization marker is set. If the agent is stopped, database statuses still change but router enforcement does not follow. If another incident for the same subscriber remains blocked, restoring one incident leaves that subscriber blocked by design. Operators should inspect both incident state and the actual owned router rules when verifying outcomes.


8. Website pages, user interface, and browser behavior


resources/views/welcome.blade.php is the public landing page and contains the login form. It includes project branding, descriptive website content, theme handling, smooth scrolling to login, and a no-account modal used by the /login fallback when a dedicated auth.login template is absent. The root route is named logout even though it only returns the welcome page. Actual logout is /logout with the name logout.action; maintainers must distinguish those names.

resources/views/admin/dashboard.blade.php renders summary counts, attack and benign series, attack-type breakdowns, destination rankings, and risk distribution from DashboardController. Time windows are all, 24h, 7d, and 30d. Attack rate is attack rows divided by all selected rows, multiplied by one hundred. The controller deliberately avoids loading a full raw log collection on the dashboard. Most metrics use intrusion_logs with a null legacy status.

DashboardController selects the earliest available timestamp for the all-time window, falling back to five years before the current time when empty. The 24-hour chart uses MySQL DATE_FORMAT to group hourly data; daily windows use DATE. The 24-hour display generates twenty-four buckets from the computed start. Seven-day and thirty-day charts generate fixed day counts. A final partial current bucket can be excluded from generated chart labels even when aggregate counters include it. All-time charts include only dates actually returned by the grouping query.

The dashboard refresh endpoint returns selectedWindowLabel, window, totalLogs, attackCount, benignCount, attackRate, chartData, attackByType, topAttackedIPs, and riskLevelDistribution. Browser code requests an initial refresh after DOM readiness and polls every fifteen seconds while visible. It uses a cache-busting query value and a no-store fetch policy and prevents overlapping refreshes. There is no WebSocket broadcast or server-sent event implementation in this path.

resources/views/admin/logs.blade.php lists raw detections with ten rows per page. LogController supports date, type, and free-text query parameters. It inspects existing columns to choose an attack-type field and search fields, preferring is_malicious, label, type, classification, verdict, then attack_type. Search candidates include PPPoE name, addresses, protocol, notes, payload, info, and ports when present. Sorting is newest created_at first. Optional notes and subscriber columns are rendered only when found in the schema.

The logs type filter is legacy-compatible rather than a strict filter on risk_level. With attack_type selected, benign rows commonly have a null family, so comparing attack_type to benign or normal does not necessarily select the same records as risk_level benign. The benign branch adds an ungrouped OR condition, which can weaken earlier predicates. These are documented implementation caveats rather than corrected in this documentation task.

resources/views/admin/manage-threats.blade.php displays incidents, not an arbitrary grouping of source-IP rows. The controller eager-loads latestLog and adapts it into a display object containing incident_id, PPPoE identity, attack family, event count, group status, and last-detected timestamp. The default status filter is unresolved, with blocked and resolved alternatives. Date filtering applies to incident last_detected_at. Each page contains ten incidents, newest activity first.

The management page shows source address, PPPoE user, destination, protocol, attack type, event count, risk label, status, and optional notes. Protocol numbers are mapped into human-readable names, including TCP, UDP, ICMP, IPv6-related values, GRE, ESP, AH, OSPF, and SCTP. Missing values use a No Value presentation. Block and Restore confirmation modals explain that enforcement is performed by the local agent. Missing subscriber identity prevents these normal actions and results in a PPPoE-unavailable or legacy-block message.

Administrators can seed two configured demonstration subscriber incidents by supplying valid destination IPs. The controller creates one unresolved incident and one attack log for each target with predefined traffic statistics and attack probability 0.99. This does not generate network packets or exercise model inference. The example data is inserted into the same tables and is not globally excluded from dashboard counts. A real subscriber with the same demo identity could later be affected by an administrator's block action.

resources/views/admin/threat-reports.blade.php presents time-window statistics and a paginated detection table. ThreatReportsController computes selected total rows, attack rows, high-risk attack rows with probability greater than 0.8, and latest row while requiring null legacy log status. The data endpoint returns up to two hundred matching rows. The CSV endpoint streams rows using a cursor and includes timestamp, addresses, risk level, attack probability, forward packet count, and byte rate.

The CSV export is not a PDF export, and it is not identical to the paginated report query: its default window is 24h, while the report index defaults to all; export does not apply the null-status filter used by index and data. The JSON search includes notes without checking whether that optional column exists. Since the inspected migrations do not create notes, a nonempty report search can fail on a schema matching only these migrations. Formula-like values are not specifically escaped for spreadsheet interpretation in the CSV writer.

resources/views/admin/system-status.blade.php renders counts, processing estimates, health indicators, and a twenty-four-hour activity timeline. It refreshes the status alert fragment every fifteen seconds using /system-status/alert. The partial maps Healthy to success styling, Caution to warning, and Warning or Critical to danger. The page does not open a live RouterOS health connection, inspect the Python processes, or issue a detector probe; its indicators are derived from stored logs.

SystemStatusController counts current day, week, and month observations; computes last-hour and last-day rates; averages forward packet count and flow_bytes_s; and calculates a probability-based health label. Critical means more than one hundred probability-at-least-0.8 rows. Otherwise Warning means more than fifty such rows or an attack rate above thirty percent. Otherwise Caution means more than twenty such rows or attack rate above fifteen percent. Otherwise Healthy is used. These indicators are mostly all-time null-status metrics, even when a selected window constrains other page counts.

The status-page uptime value is based on timestamps and is not operating-system uptime or uninterrupted service availability. In selected-window mode, the current code can treat a Carbon start-window object like a log object when accessing created_at, leaving a null timestamp and producing a failure. This path has not been validated against the live deployment. Labels describing average bytes per flow actually use the stored byte-rate field. Probability categories are dashboard conventions separate from the model's calibrated classification threshold.

resources/views/admin/live-monitor.blade.php is a demonstration page. LiveMonitorController supplies placeholder status and a current timestamp. Browser code generates random initial values and random subsequent chart changes, updating flows, packet-rate-like values, alert-like values, and timestamps. These figures are not evidence of current network activity. They should be labeled or replaced before being used in an operational report as live measurements.

Shared visual structure is repeated across the administration templates rather than centralized in a single layout file. The templates use the static Sneat administration assets, Bootstrap styling, Boxicons, ApexCharts, and shared navigation links. The public landing folder also contains a separate HTML template with Bootstrap, animations, sliders, lightboxes, counters, and PHPMailer source. Their presence does not prove that all template demonstration pages or email handlers are active Laravel features.


9. Authentication, authorization, and account lifecycle


The actual website login uses App/Models/UsersAccount mapped explicitly to users_account. LoginController validates a syntactically valid email and a required string password, finds the first matching account, and verifies the stored password hash. A successful login regenerates the session identifier and stores user, user_id, and login_time, then redirects to the dashboard. Failure redirects to the login route with an invalid-credentials message. There is no registration route or account-management interface in the inspected route file.

UsersAccount permits fullname, age, sex, email, password, and role for mass assignment. Password is hidden from model serialization. Age is cast to an integer. The name accessor maps the expected display name to fullname, allowing templates to display it. canManageThreats returns true only when role is exactly admin. The role migration adds a string column with admin as its default so existing administrator accounts retain access.

CheckSession first requires a stored user object. For every protected request it reloads the corresponding UsersAccount row, invalidates the session when the account no longer exists, and replaces the stored object with the fresh row. Role changes therefore take effect without waiting for a new login. For unsafe HTTP methods it requires canManageThreats; otherwise it aborts with 403 and a view-only message. The route group currently includes all four threat mutation endpoints.

The management Blade template separately checks canManageThreats before rendering the Actions column, per-incident action cells and modals, the demo-seed button, and the demo-seed modal. This removes the controls from viewer HTML, while middleware rejects direct crafted POST requests. Hiding a button alone would not establish authorization; both checks are used. Viewer GET requests remain permitted, including viewing blocked and resolved records, filtering, JSON refresh, and report export.

ViewOnlyUserSeeder uses updateOrCreate for user@idms.com, assigns the viewer role, sets the display name to View Only User, and hashes the requested initial password. The password itself is intentionally absent from this documentation. Re-running the seeder resets that account's password and role. DatabaseSeeder calls it and also creates the framework Test User in the separate users table. Repeated generic DatabaseSeeder runs can conflict with the unique test email; use the dedicated viewer seeder for this task.

App/Models/User is the standard Laravel Authenticatable model using the users table, with notifications, factory support, datetime verification casting, and hashed password casting. config/auth.php still points its standard provider at this model. Custom UsersAccount session login does not automatically authenticate the standard guard or establish a Sanctum token. The protected /api/user route therefore has different authentication semantics from the website pages.

Logout flushes and invalidates the session and regenerates the CSRF token. The source exposes it as GET /logout. Protected forms include CSRF tokens through the web middleware stack. The source does not configure login throttling, multifactor login, email verification enforcement, a user-account password reset flow, or a record of which administrator requested each incident transition. The account password column is not automatically hashed by UsersAccount itself; callers other than the seeder must explicitly hash new passwords.

Session configuration defaults to database storage and a ten-minute idle lifetime unless environment settings override it. Automatic browser polling may refresh request activity, depending on session handling and whether the page remains visible. The public API ingestion endpoint is outside CheckSession and outside the viewer restriction. A viewer role should therefore not be represented as a complete machine-API access-control policy.


10. Endpoint register and request responsibilities


Website GET / returns the welcome page and is named logout. GET /login returns auth.login when that view exists, otherwise the welcome page with the missing-account modal flag. POST /login invokes LoginController login. GET /logout invokes LoginController logout and is named logout.action. These routes are outside the custom protected group.

Protected GET /dashboard invokes DashboardController gotoDashboard and accepts window. GET /dashboard/refresh invokes refreshData and returns JSON aggregates for window. GET /logs invokes LogController gotoLogs and accepts date, type, q, and pagination. GET /system-status invokes SystemStatusController gotoStatus and accepts window. GET /system-status/alert returns an HTML fragment from alertFragment. GET /live renders the demonstration monitor.

Protected GET /threat-reports invokes index and accepts window and pagination. GET /threat-reports/export invokes export and returns a streamed CSV. GET /threat-reports/data invokes data, accepts window and q, and returns an object with rows. These read endpoints are available to viewers as currently implemented.

Protected GET /manage-threats invokes ManageThreatController index and accepts status, date, and pagination. POST /threats/demo invokes demo and requires valid dst_ip_jimson and dst_ip_jimson2 values. POST /threats/{id}/block invokes block for an existing incident. POST /threats/{id}/ignore invokes ignore for restoration. POST /threats/bulk-action invokes bulkAction with action and ids. All four POST operations require the admin role through CheckSession.

The block and restore methods return 404 when the incident does not exist and 422 when its PPPoE identity is blank. They update incident state and redirect back with feedback. They do not call RouterOS directly. bulkAction treats the literal block action as blocked and any other nonempty action as resolved; it does not validate an explicit action enumeration. It filters out null subscriber names but not every possible blank string, and its success count is the number of submitted IDs rather than the actual updated-row count.

Laravel API POST /api/intrusion-log invokes IntrusionLogController store. It passes the entire request array into IntrusionLog create, with Eloquent fillable fields determining persisted attributes, and responds with status saved. There is no explicit request validation, API-key verification, authentication middleware, incident assignment, or custom error response in this controller. Extra fields are not automatically preserved if absent from fillable. Records inserted through this endpoint can lack an incident link, so they may appear in log statistics without appearing in incident management.

Laravel API GET /api/user returns the standard authenticated request user and uses auth:sanctum. The API route prefix is registered through bootstrap/app.php. GET /up is the framework health route registered in that bootstrap file; no custom detector, router, or MySQL probe is defined there by the project. Console routes contain only the scaffold inspire command, rather than an IDS scheduler.

Current Flask GET / returns a running message. GET /api/features returns count and ordered features. POST /api/analyze accepts the numerical feature payload and context, returns the classification fields described earlier, and attempts direct MySQL persistence. It returns 422 for missing expected features. No batch endpoint is defined. The Flask route root and Laravel root are different services even when both use an /api path segment.

The ZIP archive setup/ids_ensemble-api-main.zip contains a historical Flask app.py with the same three route shapes but different persistence and feature behavior. It maps compact keys to older CIC-style names with spaces and capitalization, fills missing model inputs with zero rather than rejecting the request, logs the prediction, and forwards it to LARAVEL_LOG_URL using requests. Optional LARAVEL_API_KEY is added as an X-API-KEY header, with LARAVEL_TIMEOUT defaulting to eight seconds. The current Laravel ingestion route does not verify that header. The archive's behavior should not be assumed to provide incident grouping or the fourteen-feature deployed contract.

The archived model file is only 134 bytes, consistent with a Git LFS pointer placeholder rather than a complete trained estimator. A deployment using that archive requires checking its actual model artifact. The archive requirements include gunicorn and an older scikit-learn pin, but the archive does not supply proof of a current hosting configuration or production process command. Its existence explains the Render-oriented comments and default collector URL that coexist with the newer local direct-database service.


11. Database architecture, ownership, and relationships


The operational database is shared between Laravel and Python. Laravel migrations define schema and Eloquent models handle website queries and incident actions. The detector uses PyMySQL transactions to insert observations and assign incidents. The blocker uses PyMySQL to read desired incident status and mark restoration synchronization. Website, detector, and blocker must point to the same intended database and compatible schema. Their environment files are separate; matching names in source do not enforce matching live settings.

intrusion_logs stores per-analysis observations. Its id is an auto-incrementing primary key. incident_id is a nullable indexed unsigned big integer added by the incident migration. It is an application-level relationship; the migration does not define a foreign-key constraint. pppoe_name is a nullable indexed string of length one hundred. src_ip and dst_ip are nullable strings of length forty-five, allowing textual IPv6 storage even though the current collector parses IPv4 only. Ports and protocol are nullable integers.

Flow measurements comprise nullable doubles for flow_duration, flow_pkts_s, flow_bytes_s, fwd_pkt_len_mean, bwd_pkt_len_mean, fwd_iat_mean, and bwd_iat_mean; nullable integers for tot_fwd_pkts, tot_bwd_pkts, tot_fwd_bytes, and tot_bwd_bytes. risk_level is a required string of length twenty. prob_attack is a required double. attack_type is a nullable string of length one hundred. created_at and updated_at are framework timestamp columns. A nullable legacy status enum is added and modified by later migrations.

The current final legacy status enum accepts blocked and resolved, with null representing unmarked observations. An intermediate migration also allowed pending, followed by another migration reclassifying pending rows as blocked and narrowing the enum. Current incident actions update threat_incidents instead of intrusion_logs.status. Therefore a blocked incident can have observation rows whose legacy status remains null, and those observations continue contributing to null-status dashboard queries. Distinguish legacy row visibility from current incident enforcement state.

threat_incidents stores the management unit. id is its auto-incrementing primary key. pppoe_name is a nullable indexed string of length one hundred. attack_type is a nullable indexed string. status is an indexed string of length twenty, default unresolved. event_count is an unsigned integer default one. first_detected_at is the first associated observation time; last_detected_at is the most recent and is indexed. blocked_at records a block request; restored_at records a restore request; firewall_synced_at records restoration synchronization processing. All three are nullable timestamps, as are the first and last detection times. created_at and updated_at track record lifecycle.

ThreatIncident logs is a has-many relationship using incident_id. latestLog is a has-one latestOfMany relationship selecting the latest related row by the model's default aggregation identity, not explicitly by a custom created_at ordering. IntrusionLog incident is a belongs-to relationship. No PPP subscriber master table, router-rule table, explicit user-to-incident action foreign key, or normalized attack-family reference table is defined. Subscriber identity is duplicated as text in incident and detection rows.

users_account is the actual custom website account table. It contains id, fullname, nullable unsigned tiny-integer age, nullable sex enum male/female/other, unique email, hashed password text storage, timestamps, and role added later. The role column is a string default admin, not a database enum restricted to only admin and viewer. Application permission checks accept only admin for mutation; any other role value is effectively read-only in this check.

The standard users table is separate and contains id, name, unique email, nullable email_verified_at, password, remember_token, and timestamps. password_reset_tokens stores a primary email, token, and nullable creation timestamp. sessions stores a primary string id, nullable indexed user_id, nullable client IP and user agent, a long-text session payload, and indexed last_activity. The user_id column is declared as a foreignId type but no constrained relationship is added in that scaffold migration.

personal_access_tokens is a Sanctum-compatible polymorphic token table. Its fields include id, tokenable_type, tokenable_id, name, unique sixty-four-character token, nullable abilities, nullable last_used_at, nullable indexed expires_at, and timestamps. The table's presence does not mean the custom website login issues tokens. No project route for creating these tokens is present in the inspected API file.

cache contains a primary key string, medium-text value, and integer expiration. cache_locks contains a primary key string, owner, and integer expiration. jobs stores id, indexed queue, long-text payload, attempts, nullable reserved_at, available_at, and created_at integers. job_batches stores id, name, total/pending/failed counts, failed job identifiers, nullable options, nullable cancelled_at, created_at, and nullable finished_at. failed_jobs stores id, unique UUID, connection, queue, payload, exception, and failed_at defaulting to the current time. These support framework infrastructure, not the local polling loop.

Laravel's migrations bookkeeping table is managed by the framework, rather than explicitly created in these application migrations. It records which migrations ran and their batch numbers. The file inventory also includes an optional local SQLite file if present; its existence is not proof that production uses SQLite. Several migration and query statements are MySQL-specific, so switching the full application to SQLite requires compatibility work even though isolated tests use SQLite.


12. Migration history and data transformation rules


The scaffold migrations create users, password reset tokens, sessions, cache tables, and queue tables. December 2025 migrations create intrusion_logs, personal access tokens, users_account, and a nullable intrusion-log status enum. June 2026 migrations broaden the status enum temporarily, backfill timestamps, reclassify pending statuses, and change one demo destination address. August 2026 migrations introduce PPPoE identity and incident tracking. October 2026 adds account roles.

The timestamp backfill replaces missing created_at or updated_at using the other timestamp and then the current database time. It has no meaningful reverse operation. The pending-status reclassification changes existing data, so a down migration that reopens the enum cannot reconstruct which blocked rows were formerly pending. The demo destination migration changes every matching destination address, not only rows explicitly marked as demonstrations, and its reverse similarly changes every matching replacement address.

The PPPoE identity migration adds the nullable indexed name column only if absent, then backfills two known demonstration source addresses to their configured subscriber names. It does not discover names for all historical observations. The incident migration creates indexed incident columns and adds nullable indexed incident_id to intrusion_logs without a database foreign key.

For historical attack logs, the incident migration reads all matching rows into memory, orders by ID, and groups by lowercased trimmed subscriber name, attack family, and legacy status. Each status group becomes a separate incident. Its first and last timestamps are taken from the first and last ID-ordered logs, rather than computing strict minimum and maximum timestamps. event_count equals group size. Legacy blocked and resolved values are retained; other values become unresolved. Each original row is linked to its incident. This historical grouping does not use the detector's fifteen-minute live grouping window.

Rolling back the incident migration drops the links and incident table, losing the new incident-management state. Applying migrations on a live database should be preceded by an appropriate backup and review of pending migrations. The targeted role migration used during the hosting walkthrough changes only users_account role, preserving existing account behavior with its admin default. The viewer account is created by a separate seeder; adding the role column alone does not create it.


13. Machine-learning training, artifacts, and recorded results


The maintained deployment training path is setup/Training/train_netflow_model.py with the contract in training_schema.py. The training README explicitly says it replaces the defective notebook path for deployment. Historical notebooks and manuscripts describe stacking ensembles and different thresholds; the current maintained script uses HistGradientBoostingClassifier for Stage A and RandomForestClassifier for Stage B. The project can still be described as a two-stage model, but the exact active estimators should be named accurately.

The dataset loader scans CSV files in the selected dataset directory, normalizes column names with Unicode normalization and non-alphanumeric replacement, locates a label-like column, and requires every feature in NETFLOW_FEATURES. It retains the fourteen numerical features, a normalized attack-family label, a capture filename, and a binary label determined by whether the normalized family is BENIGN. Numeric failures become missing values and infinities are replaced with missing values.

Optional max-rows-per-file sampling processes CSV chunks of fifty thousand rows, assigns reproducible random keys, and retains the smallest keys as a uniform sample across the file rather than simply taking the first records. The random seed begins at forty-two and varies by file index. The full dataset path loads all records. The source requires both binary classes and at least two attack families before training.

The split is seventy percent training, fifteen percent validation, and fifteen percent test, formed by a thirty-percent holdout followed by a half split. Stratification is on the binary label. It is not a capture-disjoint or time-disjoint split, even though capture filenames are retained. Related traffic from the same capture can therefore appear in more than one partition. This limits claims about generalization to unseen networks or future capture periods.

Each stage has its own cloned preprocessing pipeline: median imputation, StandardScaler, and a ColumnTransformer selecting the explicit feature list and dropping other columns. Independent cloning prevents Stage B from overwriting Stage A preprocessing state. Stage A uses two hundred maximum histogram-gradient-boosting iterations, learning rate 0.08, maximum thirty-one leaf nodes, balanced class weights, and random state forty-two. Stage B uses two hundred random-forest trees, maximum depth twenty-four, balanced-subsample weighting, all available jobs, and the same random state.

Stage A trains on all training rows and binary labels. Stage B trains only on training rows labeled attack and their family labels. select_threshold computes the precision-recall curve on validation probabilities, finds thresholds meeting target recall, and chooses the highest precision among those candidates. The default target recall is 0.95; invalid target values are rejected by argument parsing. The threshold is not chosen on the final test partition in the maintained script.

The bundle stores bin, mul, features, best_threshold, schema_version, dataset_profile, trained_at, and config. Configuration includes run type, sampling limit, random state, target recall, row count, and training elapsed time. dataset_profile is cicids-bootstrap. Full training defaults to setup/data/model/netflow_ids.joblib; a sampled run defaults to netflow_ids.smoke.joblib so it does not overwrite the full artifact. An explicit output argument can change either destination.

The trainer saves and reloads the artifact before evaluation and verifies that Stage A and Stage B do not share the same fitted preprocessor object. It computes full-test predictions using the stored threshold and writes a neighboring metrics JSON. A reproducible balanced check selects up to one hundred benign and one hundred attack rows from the untouched test partition. Small smoke datasets are marked incomplete when they cannot supply two hundred rows. The animated activity bar reports activity and elapsed time, not a trustworthy completion percentage.

The checked-in netflow_ids.metrics.json records a full run with schema mikrotik-netflow-v1 and threshold approximately 0.9865455954. Its full binary test matrix records 340751 true benign, 214 false-positive benign, 3537 missed attacks, and 80110 detected attacks across 424612 rows. Accuracy is approximately 99.1166 percent. Attack precision is approximately 99.7336 percent, attack recall 95.7715 percent, and attack F1 97.7124 percent. These are stored historical evaluation results, not measurements rerun for this documentation.

The balanced check records one hundred benign and one hundred attack rows, with one hundred benign correctly classified and ninety-seven attacks detected, giving 98.5 percent binary accuracy. Its attack-family report lists DDOS, DOS GOLDENEYE, DOS HULK, PORTSCAN, and SSH-PATATOR in that sample, with perfect family predictions on the selected true-attack rows. Family evaluation on true attacks is separate from end-to-end gated performance; missed attacks do not become operational family alerts even when Stage B would label them correctly in isolation.

The metrics file explicitly warns that CICIDS bootstrap results are not production validation and calls for labeled captures from the actual MikroTik environment. The old manuscripts' claims such as 99.92 percent binary accuracy or 99.83 percent multiclass accuracy must be attributed to those manuscripts and not substituted for the maintained artifact's metrics. Neither a metrics filename nor a repository copy proves that the live detector loaded that exact artifact or threshold.

The Dataset folder contains eight capture CSV files covering Monday working hours, Tuesday, Wednesday, Thursday morning web attacks, Thursday afternoon infiltration, Friday morning, Friday afternoon port scans, and a DDoS dataset. They are input material, not application runtime tables. Their individual names and sizes are included in the inventory. The full CSV payloads and serialized estimator internals are not reproduced in a prose reference.

Prepare a monitoring host with a compatible Python interpreter and install setup/data/requirements.txt into an appropriate environment. Place a trusted compatible model bundle in setup/data/model and configure setup/.env for router access, database connectivity, inference URL, and optional thresholds and polling intervals. Configure the router's Traffic Flow export to the monitoring host and verify that port 2055 traffic and RouterOS API access are reachable. The repository's current collector requires NetFlow version five.

Prepare Laravel using Composer dependencies, the application environment, an existing valid application key, and the intended database. Ensure storage and bootstrap/cache are writable by the web process. Point the site's document root to Laravel public where hosting permits. Build frontend source assets if the deployment uses their Vite outputs. Run reviewed migrations and only the intended seeders. 17. Operational limitations and accurate interpretation


The system is flow-based and periodically aggregates per-subscriber records. It does not inspect full packet payloads, decrypt TLS, provide signature updates, reconstruct every session, or prove compromise from a probability alone. A subscriber aggregate can contain many unrelated conversations. Displayed destination metadata is context from one latest record rather than a complete explanation of the prediction. Exporter configuration, filtering, and feature approximations influence what is observed.

Network availability is a dependency in several directions: router to collector UDP, collector to inference HTTP, detector to MySQL, Laravel to MySQL, blocker to MySQL, and blocker to RouterOS. An online website does not imply those local links are healthy. Historical log statistics can remain visible when collection has stopped. The system-status and live-monitor pages do not provide reliable independent process-liveness checks in their current implementation.

The current Flask API lacks source authentication and runs its direct entrypoint with debug enabled on all interfaces. RouterOS pools use unencrypted API settings. The Laravel ingestion API accepts mass-assigned permitted fields without explicit validation or API authentication. These are concrete source observations. Deployment should establish appropriate access boundaries, transport protections, request validation, and production process configuration rather than assuming website roles cover machine interfaces.

Database failure is logged but not returned as an inference error. There is no durable store-and-forward buffer or end-to-end message identifier. Incident creation lacks a unique eligibility constraint. Timestamp sources differ: Python uses host-local datetime, Laravel config declares UTC, browser timestamps use browser locale, and database synchronization uses NOW. Without consistent timezone configuration and clock synchronization, time filters, incident windows, uptime estimates, and activity charts can be misleading.

The viewer role is enforced on unsafe requests inside the protected web group. It does not automatically cover future mutations added outside that group, future GET endpoints that change state, or the separate ingestion API. The account role defaults to admin for compatibility; newly created custom accounts should have an explicit intended role. The initial viewer password is a user-requested setup credential, not a recommended permanent access policy, and is omitted here.

Status has two meanings in the database: legacy observation status and current incident status. Dashboard null-status filters do not mean no currently blocked subscriber contributed those observations. Incident event_count summarizes linked detections and may diverge if logs are inserted through an alternate path or manipulated independently. No database foreign key prevents orphaned incident links. The optional notes field is referenced in some paths without a matching migration in this snapshot.

Restoration synchronization is not fully verified by the current subscriber cleanup path because deletion failures can be swallowed. Block requests are not marked with a corresponding success acknowledgement and continue reconciliation. A new drop rule may not be effective if earlier router rules accept or FastTrack the traffic. Removing an IDS-owned drop rule cannot override unrelated firewall rules, service outages, upstream failures, or PPP account restrictions; a resolved incident therefore does not guarantee working internet service.

Historical research describes broader claims and architectures, including packet-based capture, stacking ensembles, and high benchmark scores. Those materials preserve project rationale but do not override current code. Current maintained training is a NetFlow-compatible bootstrap pipeline with a documented distribution gap. Production validation should use labeled data from the actual environment and separately measure false positives, missed attacks, family confusion, decision latency, and operational impact.


18. Maintenance, troubleshooting, and glossary


When no detections appear, inspect the collector console and merged_ids.log for accepted NetFlow version-five records, verify the exporter sender matches MIKROTIK_HOST, check excluded address prefixes, verify PPP discovery, and confirm at least ten records exist for the selected client. Consider queue length and traffic-driven timers before assuming the classifier is failing. Then confirm the configured API_URL targets the intended current detector rather than an older hosted API.

When inference rejects a request, compare /api/features against the sender's normalized keys and the training schema. Missing-model-features errors indicate a contract mismatch; present but malformed values may instead be coerced to zero. When inference succeeds but the website is unchanged, check database-save errors and the intended database/table settings, since an HTTP success does not certify persistence. Compare observation timestamps and avoid using the synthetic live-monitor values as a diagnostic.

When a block badge appears but traffic continues, verify the local agent is running, inspect blocked_threat_sync.log, confirm the subscriber currently has an active PPP session, inspect owned firewall rules and their source address, review rule order and FastTrack, and inspect connectivity to both database and router. When restoration does not work, check for another blocked incident for the same name, failed removal fallbacks, unrelated router rules, and whether the synchronization marker was set despite residual rules.

Keep the classifier bundle, ordered features, schema version, training script, metrics file, and runtime dependency versions together as a release unit. Keep website code, Python writers, and database schema compatible during upgrades. Maintain backups for operational rows, account data, incident state, and trusted model artifacts; runtime prediction and enforcement logs support diagnosis but do not replace database backups. Log rotation and retention are not implemented in the Python file handlers.

PPPoE means Point-to-Point Protocol over Ethernet; its username is treated as the stable subscriber identity. RouterOS is the MikroTik router operating system and API target. NetFlow is exported traffic-summary telemetry. A flow record summarizes traffic counters and endpoints rather than holding packet content. Forward traffic is traffic where the selected subscriber is source; backward traffic is traffic where it is destination. IAT means inter-arrival time, although the collector's stored IAT fields are aggregate approximations.

Stage A is binary benign-versus-attack inference. Stage B is attack-family inference gated by Stage A. A threshold converts attack probability to a decision. Precision describes the proportion of predicted attacks that are truly attacks in an evaluated dataset; recall describes the proportion of actual attacks detected; F1 combines precision and recall. Bootstrap metrics are development evidence from a surrogate dataset, not deployed accuracy. An incident is a management record linking observations for a subscriber and family according to grouping rules.

Unresolved means awaiting an administrator decision. Blocked means the agent should maintain a subscriber-owned drop rule. Resolved means restoration has been requested and the incident remains in history. firewall_synced_at is the agent's restoration-processing marker with the verification limitations described earlier. CSRF protects browser state-changing requests against cross-site forgery within the web stack. Sanctum is the separate Laravel token/session authentication infrastructure, not the custom UsersAccount login itself.

The final inventory lists project files while grouping installed dependencies, private runtime data, and generated caches by category.

Two-Stage Ensemble Machine Learning for Network Intrusion Detection System

ABSTRACT

This paper presents a novel two-stage ensemble machine learning approach for network intrusion detection systems (IDS). The proposed method employs a calibrated stacking ensemble for binary classification (Stage A) followed by a Random Forest classifier for multi-class attack categorization (Stage B). Evaluated on the CIC-IDS2017 benchmark dataset, our approach achieves 99.92% binary classification accuracy and 99.83% multi-class accuracy across 14 attack types, significantly outperforming existing methods. The system demonstrates robust performance on network-layer attacks including DDoS, PortScan, and various DoS variants, providing an effective solution for modern network security challenges.

Keywords: intrusion detection, ensemble learning, machine learning, network security

INTRODUCTION

The rapid expansion of network infrastructures and the increasing sophistication of cyber threats have made intrusion detection systems (IDS) a critical component of organizational security frameworks (Ring et al., 2019). Traditional signature-based detection methods struggle to identify novel attacks and zero-day exploits, leading to the adoption of machine learning approaches for anomaly detection (Buczak & Guven, 2016). As noted by Sommer & Paxson (2010), machine learning for intrusion detection must operate outside the 'closed world' assumption, dealing with unpredictable and novel attack behaviors—a challenge our two-stage ensemble is designed to address.

Several benchmark datasets have been developed for evaluating IDS performance, including KDD CUP 99 (Tavallaee et al., 2009), UNSW-NB15 (Moustafa & Slay, 2015), and more recently, CIC-IDS2017 (Sharafaldin et al., 2018). The CIC-IDS2017 dataset addresses limitations of earlier datasets by providing realistic network traffic with diverse attack scenarios (Ring et al., 2019). However, effective utilization of these datasets requires sophisticated machine learning approaches that can handle class imbalance and complex attack patterns.

Ensemble learning methods have shown remarkable success in intrusion detection by combining multiple classifiers to improve overall performance (Kevric et al., 2017). Random Forests (Breiman, 2001) and Gradient Boosting (Friedman, 2001) have been particularly effective, with recent advancements in stacking ensembles (Wolpert, 1992) and XGBoost (Chen & Guestrin, 2016) demonstrating superior performance. However, many existing approaches suffer from poor probability calibration (Niculescu-Mizil & Caruana, 2005) and suboptimal threshold selection (Zadrozny & Elkan, 2002). Chandola et al. (2009) conducted a seminal survey on anomaly detection, framing many of the foundational challenges that our two-stage ensemble aims to overcome through calibrated probability estimation and threshold optimization.

This paper proposes a two-stage ensemble framework that addresses these limitations through calibrated probability estimation and optimized threshold tuning. Our contributions include: (1) a novel two-stage architecture separating binary detection from multi-class classification, (2) implementation of calibrated stacking ensembles for robust probability estimation, and (3) comprehensive evaluation on the CIC-IDS2017 dataset demonstrating state-of-the-art performance.

LITERATURE REVIEW

Intrusion Detection Datasets

The evolution of intrusion detection datasets has significantly influenced machine learning approaches in cybersecurity. Early datasets like KDD CUP 99 (Tavallaee et al., 2009) established foundational benchmarks but suffered from redundancy and unrealistic traffic patterns. The UNSW-NB15 dataset (Moustafa & Slay, 2015) addressed some limitations by incorporating modern attack scenarios, while CIC-IDS2017 (Sharafaldin et al., 2018) provided more realistic network behavior and diverse attack profiles (Ring et al., 2019).

Ring et al. (2019) conducted a comprehensive survey of network-based intrusion detection datasets, highlighting the importance of realistic traffic generation and proper attack characterization. Their analysis emphasized that dataset quality directly impacts the practical applicability of developed IDS solutions. Khraisat et al. (2019) provided a comprehensive survey of intrusion detection systems, highlighting the challenges of imbalanced datasets and evolving attack patterns, which further underscores the need for robust ensemble methods like the one proposed in this work. Sperotto et al. (2010) provided an overview of IP flow-based intrusion detection, which informs our feature selection process focused on flow-level statistics.

Ensemble Learning in Intrusion Detection

Ensemble methods have gained prominence in intrusion detection due to their ability to improve accuracy and robustness. Breiman's (2001) Random Forests provided the foundation for many ensemble approaches, while Friedman's (2001) Gradient Boosting introduced sequential improvement of weak learners. Chen and Guestrin (2016) further advanced gradient boosting with XGBoost, incorporating regularization and efficient implementation.

Recent studies have explored stacking ensembles (Wolpert, 1992) for intrusion detection. Kevric et al. (2017) demonstrated that combining classifier approaches using tree algorithms can be effective for network intrusion detection. Similarly, Aljawarneh et al. (2018) proposed an ensemble-learning framework that improved IDS efficiency through classifier combination and feature selection. These approaches align with Wolpert's (1992) stacked generalization theory, which forms the theoretical basis for our ensemble design. Ahmed et al. (2016) surveyed network anomaly detection techniques and emphasized the growing role of machine learning in identifying subtle and sophisticated threats, reinforcing the relevance of our ensemble-based approach. Almseidin et al. (2017) evaluated multiple machine learning algorithms for IDS, demonstrating the superiority of ensemble methods, which supports our choice of a stacking-based architecture.

Probability Calibration and Threshold Optimization

Probability calibration is crucial for reliable intrusion detection, as noted by Niculescu-Mizil and Caruana (2005). Platt scaling (Platt, 1999) and isotonic regression (Zadrozny & Elkan, 2001) have been widely used to transform classifier scores into accurate probability estimates. Zadrozny and Elkan (2002) demonstrated that proper calibration significantly improves classification performance, particularly for imbalanced datasets common in intrusion detection.

Recent works by Mirsky et al. (2018) and Kasongo & Sun (2020) have incorporated calibration techniques in ensemble frameworks, showing improved detection rates. Our approach builds upon these foundations by integrating calibration directly into the stacking ensemble architecture.

RESEARCH METHODOLOGY

Dataset and Preprocessing

We utilized the CIC-IDS2017 dataset (Sharafaldin et al., 2018), which contains realistic network traffic with both benign and attack flows. The dataset includes 2.8 million samples across 80 features, capturing various attack scenarios over multiple days. Following the dataset characterization by Sharafaldin et al. (2018), we focused on network-layer attacks detectable through flow statistics. Haider et al. (2017) discussed the importance of realistic dataset generation using fuzzy qualitative modeling, which aligns with our use of the CIC-IDS2017 dataset to ensure real-world applicability.

Data preprocessing involved several steps. First, we normalized column names and handled missing values by replacing them with zeros. Numerical features were standardized using StandardScaler, while non-numeric identifiers were excluded to prevent data leakage. The label column was processed using Unicode normalization to ensure consistency across different attack naming conventions.

Feature Selection

Based on the analysis by Garcia et al. (2014), we selected 78 numerical features representing network flow characteristics. Features related to pure identifiers (IP addresses, ports, timestamps) were excluded, while behavioral features like flow bytes per second, packets per second, and inter-arrival times were retained. This approach aligns with feature selection strategies discussed by Aljawarneh et al. (2018) for handling high-dimensional network data.

To address probability calibration, we incorporated CalibratedClassifierCV with sigmoid calibration (Niculescu-Mizil & Caruana, 2005; Platt, 1999), which has shown effectiveness in cybersecurity applications (Zadrozny & Elkan, 2001).

Machine Learning–Based Intrusion Detection System using Stacking Ensemble Method

INTRODUCTION

Cybersecurity has become a critical issue in the digital age, as networks grow increasingly complex and vulnerable to attacks. Traditional signature-based intrusion detection systems (IDS) are limited because they cannot recognize new or evolving attack types. As a result, machine learning (ML)–based IDS have emerged as a promising solution for detecting anomalies and threats by learning traffic behavior patterns rather than relying solely on known signatures.

Modern algorithms such as Random Forest (Breiman, 2001), Gradient Boosting (Friedman, 2001), and XGBoost (Chen & Guestrin, 2016) are now widely applied to network intrusion detection. However, despite their strengths, single-model IDS still face challenges in achieving consistent accuracy across different attack categories and in maintaining generalization to unseen threats.

This study proposes an enhanced IDS architecture using ensemble learning—specifically a stacking model that combines multiple base classifiers (Random Forest, Gradient Boosting, and XGBoost) with a meta-learner (Logistic Regression). By leveraging the CICIDS2017 dataset (Sharafaldin et al., 2018), this research evaluates both binary (benign vs. attack) and multi-class (attack family) classification to determine how stacking ensembles improve detection accuracy and robustness.

STATEMENT OF THE PROBLEM

Machine learning models for IDS often exhibit high binary accuracy but fail when distinguishing between specific attack families. This issue is amplified by imbalanced datasets and temporal differences between training and testing data. The problems addressed by this study are:

How can stacking ensemble learning improve IDS accuracy and generalization compared with single classifiers?

What are the detection results of the ensemble model when distinguishing between benign and attack traffic?

Why does multi-class performance drop despite strong binary detection accuracy, and what factors cause it?

How can probability calibration and threshold optimization improve classification decisions?

OBJECTIVE OF THE STUDY

To develop a machine learning–based network intrusion detection system using stacking ensemble models for enhanced performance in detecting and classifying network attacks.

To preprocess and analyze the CICIDS2017 dataset for machine learning-based IDS development.

To design a stacking ensemble architecture integrating Random Forest, Gradient Boosting, and XGBoost classifiers.

To train and evaluate binary and multi-class models using accuracy, precision, recall, F1-score, and ROC-AUC metrics.

To assess the effect of probability calibration on improving decision thresholds.

To compare the ensemble’s results against known single-model baselines in existing studies.

SIGNIFICANT OF THE STUDY

This research contributes to the continuous evolution of intrusion detection by showing how ensemble learning enhances classification reliability and detection precision. Stacking models allow the combination of multiple algorithms to capture both linear and nonlinear relationships in data, reducing bias and variance simultaneously (Wolpert, 1992).

The findings will benefit cybersecurity practitioners by offering a scalable model for real-time IDS deployment and aid academic researchers by providing a structured methodology for building robust, calibrated ensemble models. It also highlights the role of threshold tuning (Zadrozny & Elkan, 2002) and probabilistic calibration (Platt, 1999) in improving confidence scoring for IDS decisions.

SCOPE AND DELIMITATION

This study focuses on the use of supervised learning and ensemble methods for IDS development using the CICIDS2017 dataset. The dataset includes a wide range of network traffic representing benign and malicious behaviors. Only numeric flow-based features were analyzed; packet payloads and protocol headers were excluded.

The study is delimited by:

Dataset: CICIDS2017 only.

Algorithms: Random Forest, Gradient Boosting, and XGBoost combined via stacking.

Platform: Python (scikit-learn, XGBoost).

Evaluation: Offline performance testing; no live or hardware-integrated IDS deployment.

Deep learning and hybrid neural network methods are excluded, as the primary goal is to validate the efficacy of tree-based ensembles for classical IDS.

METHODOLOGY

A. Dataset Preparation

The dataset (Sharafaldin et al., 2018) consists of over 2.8 million instances from eight separate capture files. Each CSV file represents a unique network scenario. Data cleaning involved normalization of column names, removal of identifiers (IP addresses, timestamps), conversion of all features to numeric types, and imputation of missing values.

B. Labeling

Each record was labeled as either Benign or Attack (binary) and further assigned a detailed attack type for multi-class analysis. Unicode and inconsistent naming issues were corrected to standardize labels.

C. Model Design

A stacking ensemble was implemented using Random Forest (Breiman, 2001), Gradient Boosting (Friedman, 2001), and XGBoost (Chen & Guestrin, 2016) as base learners, and Logistic Regression as the meta-learner. Calibration (Niculescu-Mizil & Caruana, 2005) with the sigmoid method was applied to optimize probability outputs.

D. Training and Testing

A time-based split was used: the final capture (“Wednesday-workingHours”) served as the test set. Stage A trained a binary classifier; Stage B trained a multi-class classifier. Model evaluation used accuracy, precision, recall, F1-score, and ROC-AUC metrics.

E. Implementation Tools

The implementation was coded in Python using scikit-learn, xgboost, and supporting libraries (pandas, numpy, joblib). Training was performed on a multi-core CPU environment.

RESULT AND DISCUSSION

A. Binary Classification (Stage A)

The ensemble achieved outstanding performance:

Accuracy: 96.48%

Precision: 0.945

Recall: 0.959

F1-score: 0.952

ROC-AUC: 0.972

These results confirm the capability of ensemble stacking to improve detection performance, surpassing typical single-model baselines such as Decision Trees or Logistic Regression (Ali et al., 2023; Alotaibi, 2023). The calibrated probability threshold of 0.053 optimized recall while maintaining high precision.

B. Multi-Class Classification (Stage B)

The multi-class model failed to generalize effectively because the test set contained unseen attack types. This outcome aligns with the findings of Buczak and Guven (2016) and Ring et al. (2019), who observed significant class imbalance and label mismatch issues in IDS datasets. The model correctly identified general attack behavior but failed to classify new attack subtypes—highlighting a dataset limitation rather than a model defect.

C. Interpretation and Comparison

Studies such as Mahfouz et al. (2022), Talukder et al. (2024), and Pramanick et al. (2025) reported similar results where ensemble methods achieved excellent binary detection but struggled in open-set conditions. The proposed model’s strong ROC-AUC validates that ensemble probability calibration improves confidence scores, as previously discussed by Zadrozny and Elkan (2001, 2002).

D. Implications

These results emphasize the need for consistent attack label mapping (Lazzarini, 2023), integration of diverse datasets (Moustafa & Slay, 2015), and hierarchical classification approaches. The system’s strength in binary detection demonstrates potential for real-time IDS integration once retrained with broader data coverage.

CONCLUSION AND RECOMMENDATION

This study developed and evaluated a stacking ensemble-based network intrusion detection model using the CICIDS2017 dataset. The system achieved 96.48% accuracy in binary detection, demonstrating that ensemble learning effectively improves detection precision and robustness. However, its poor performance in multi-class classification underscores the importance of dataset balance and representativeness.

Recommendations

Group related attack subtypes into unified families (e.g., all DoS variants → DDoS).

Expand dataset diversity by merging other benchmark datasets (e.g., UNSW-NB15, NSL-KDD).

Explore hybrid ensemble-deep learning models for enhanced feature extraction.

Incorporate open-set recognition techniques to handle unseen attacks.

Implement real-time experiments to evaluate response latency and deployment feasibility.

Design and Development of a Real-Time Flow-Based Intrusion Detection and Security Management System Using a Two-Stage Ensemble Model

Jimson A. Olaybar1, Patrick D. Cerna2

1,2College of ICT and Engineering, State University of Northern Negros, Sagay City, Negros Occidental, Philippines

1FCSIT, Southern Leyte State University – Main Campus, Sogod, Southern Leyte, Philippines

Abstract— The increasing complexity of modern network environments has heightened the need for practical and scalable intrusion detection solutions. This study presents the development of a real-time, flow-based Intrusion Detection and Security Management System (IDSMS) that integrates live traffic monitoring, machine learning-based intrusion analysis, centralized data storage, and web-based visualization. The system captures network traffic from a MikroTik-based gateway using a passive flow sniffer deployed on a Kali Linux monitoring node. Packets are aggregated into bidirectional flows and transformed into statistical feature vectors, which are analyzed by a machine learning inference service through an application programming interface. Detection results, including risk level and attack classification, are stored in a centralized database and presented through an interactive dashboard. Development-stage testing using simulated attack traffic demonstrates the system’s ability to capture, analyze, and visualize network threats in real time. The proposed system provides a practical foundation for deployment in shared-access networks, small enterprises, and IoT-enabled environments.

Keywords— Intrusion Detection System, Flow-Based Analysis, Machine Learning, Network Security, Real-Time Monitoring

INTRODUCTION

The rapid growth of networked systems, including enterprise networks, Internet cafés, public Wi-Fi services, and IoT-enabled environments, has significantly increased exposure to cyber threats. Modern attacks such as port scanning, brute-force login attempts, DNS amplification, and distributed denial-of-service (DDoS) attacks continue to evolve in scale and sophistication, making traditional signature-based intrusion detection systems (IDS) insufficient for real-time protection [1], [4].

Recent studies emphasize the effectiveness of flow-based intrusion detection, which analyzes statistical properties of network flows rather than packet payloads. This approach enables efficient monitoring of encrypted traffic while reducing computational overhead, making it suitable for real-time and resource-constrained environments [2], [3], [7]. Machine learning (ML) and deep learning techniques further enhance flow-based IDS by learning complex traffic patterns and improving anomaly detection accuracy [6], [14], [22].

Despite advances in detection models, many existing IDS studies focus primarily on offline datasets and lack full system integration, limiting their applicability in operational networks [4], [10]. Real-world deployment requires not only accurate models but also live traffic capture, scalable inference, centralized logging, and actionable security management interfaces. Furthermore, public-access networks such as pisonet or shared Wi-Fi services demand IDS solutions capable of identifying malicious client devices while preserving normal user traffic. Recent studies have demonstrated the feasibility of anomaly detection and traffic pattern analysis in real-world Pisonet environments using dynamic time warping and seasonal decomposition techniques [25], [26].

To address these challenges, this study presents the development and implementation of a real-time flow-based Intrusion Detection and Security Management System (IDSMS). The proposed system integrates live network traffic capture, flow-level feature extraction, machine learning-based attack classification, and a web-based security management platform. The system is designed to operate with a MikroTik gateway and downstream routers, enabling visibility into client-generated traffic while supporting real-time detection and response.

Unlike dataset-only approaches, this work emphasizes end-to-end system development, demonstrating how flow-based IDS concepts can be operationalized into a working security platform. The system architecture supports live monitoring, historical analysis, and threat management, providing a practical foundation for deployment in small enterprise networks, IoT environments, and public internet access services.

RELATED WORKS

Flow-based intrusion detection has become a widely adopted approach for modern network security due to its scalability, privacy-preserving nature, and compatibility with encrypted traffic. Unlike payload inspection, flow-based methods rely on statistical representations of communication behaviors, enabling real-time monitoring with reduced computational overhead. Satheesh et al. demonstrated early integration of flow-based anomaly detection with SDN/OpenFlow environments using machine learning, highlighting the feasibility of flow-driven security monitoring in programmable networks [1]. Similarly, Pontes et al. proposed a novel flow-based detection method using the inverse Potts model, showing that flow representations can capture complex network behaviors beyond traditional feature engineering [2]. For Wi-Fi environments, Segura-Garcia et al. introduced HeaderHunter, a real-time flow-based IDS for IEEE 802.11 networks, supporting the practicality of flow-level monitoring for wireless systems [3].

A major challenge in flow-based IDS research is the inconsistency of feature definitions and dataset variability across studies. Sarhan et al. emphasized the need for standardized feature sets, reporting that differences in feature extraction and labeling procedures can limit reproducibility and deployment readiness [4]. In parallel, dataset contributions have improved realism and diversity for IDS evaluation. Ferrag et al. introduced Edge-IIoTset, a comprehensive dataset reflecting realistic IoT and IIoT cyberattacks for centralized and federated learning scenarios [5]. Benchmarking studies using widely adopted datasets such as CICIDS2017 further demonstrate the importance of feature relevance and model robustness. Kurniabudi et al. analyzed CICIDS2017 features using information gain for anomaly detection, while Maseer et al. provided benchmarking of machine learning models for anomaly-based IDS, reinforcing the need for systematic model evaluation when using flow-style datasets [10], [11]. Komisarek and Pawlicki also introduced a refined dataset specifically oriented toward real-time NIDS settings, highlighting the continued effort to align IDS datasets with operational requirements [12].

Deep learning has increasingly been applied to flow-based intrusion detection due to its capability to model nonlinear relationships and hierarchical traffic patterns. Vishwakarma and Kesswani proposed a deep neural network-based real-time IDS for IoT, reporting improved detection performance in IoT contexts [6]. Additional studies have focused on flow-driven deep learning models for IoT anomaly detection, reflecting the shift toward learning-based approaches that operate effectively under constrained device environments [7], [8]. More recent developments include transformer-based architectures designed explicitly for flow representations. Manocchio et al. proposed FlowTransformer, demonstrating that attention-based models can effectively learn temporal and contextual dependencies within flow records [20]. These studies suggest that advanced deep learning can enhance detection accuracy; however, deploying such models in practical settings requires stable feature extraction pipelines and system-level integration.

Beyond centralized learning, federated learning (FL) has emerged as a promising technique for privacy-preserving intrusion detection across distributed networks. de Oliveira et al. presented F-NIDS, demonstrating a federated approach for intrusion detection while reducing the need to centralize sensitive data [13]. Doriguzzi-Corin and Siracusa proposed FLAD, which adapts federated learning for DDoS detection using adaptive mechanisms to address dynamic network behaviors [21]. Other works further explored combining FL with generative or representation learning methods. Nugraha et al. investigated federated learning with variational autoencoders for anomaly detection, indicating that hybrid FL approaches can improve generalization across heterogeneous sites [22]. Devine et al. also discussed federated ML for enabling IDS in IoT networks, while Buyuktanir et al. reviewed FL applications in IDS, outlining research trends and open challenges such as non-IID traffic distributions and communication overhead [23], [24].

Several studies have also proposed enhancement techniques to improve intrusion detection reliability, including data augmentation and improved feature encoding. Mohammad et al. explored deep learning combined with data augmentation to enhance IDS performance, supporting the importance of improving training robustness and generalization [14]. Alitbi et al. proposed a generalized real-time IDS using incremental feature encoding and similarity embedding, addressing real-time constraints while improving discrimination capability [15]. These contributions reinforce the direction of building models and representations that are more suitable for live deployment and continuous monitoring.

Despite extensive research on flow-based IDS models, feature engineering, and learning strategies, many studies remain focused on algorithmic accuracy and offline experiments, with limited emphasis on full operational deployment. Practical deployment requires an integrated pipeline covering real-time flow capture, feature extraction consistency, scalable inference, centralized storage, and a management interface to support monitoring and response. The present work addresses this gap by developing an end-to-end Intrusion Detection and Security Management System (IDSMS) that connects live flow sniffing, machine learning inference via API, database logging, and a web-based dashboard for monitoring and threat management. By focusing on system development and implementation, this study complements model-centric IDS research and supports practical applicability in environments such as small enterprise networks and public-access Wi-Fi infrastructures. Recent work has further extended flow-based analysis to real-world scenarios, including Pisonet traffic analysis [25] and dynamic network traffic visualization using machine learning and seasonal decomposition [26].

METHODOLOGY

The detection models integrated into the system are based on the previously developed and validated two-stage ensemble intrusion detection framework.

System Architecture Overview

The proposed IDSMS follows a modular, flow-based architecture composed of five primary components: (1) live traffic capture, (2) flow aggregation and feature extraction, (3) machine learning-based intrusion analysis, (4) centralized data storage, and (5) web-based visualization and threat management. Figure 1 illustrates the complete system workflow, from packet capture to security decision-making.

Figure 1. Overall System Architecture Diagram

Network traffic originates from client devices connected to routers and passes through a MikroTik gateway. A dedicated monitoring node running Kali Linux captures and processes traffic flows without interfering with network operations.

Live Traffic Capture and Flow Aggregation

Traffic capture is performed using a Python-based flow sniffer deployed on the Kali Linux virtual machine. The sniffer passively listens on the designated network interface connected to the MikroTik router. Packets are aggregated into bidirectional flows using a five-tuple identifier consisting of source IP address, destination IP address, source port, destination port, and transport protocol.

Flow-based monitoring is selected due to its proven effectiveness in detecting network anomalies while remaining compatible with encrypted traffic [1], [3]. Idle timeout mechanisms are employed to determine flow termination, ensuring timely feature export for real-time analysis.

Feature Extraction and Preprocessing

For each completed flow, the system extracts a comprehensive set of approximately 78 statistical features, following best practices in flow-based IDS research [4], [7], [10]. These features capture temporal, volumetric, and directional characteristics of traffic, including flow duration, packet counts, byte rates, inter-arrival times, and forward–backward packet statistics.

Figure 2. Runtime Data Processing Pipeline of the Proposed IDSMS

Prior to analysis, flows are filtered to remove incomplete or insignificant traffic, such as flows with insufficient packet counts. Feature normalization is applied to ensure compatibility with the trained machine learning models and to prevent dominance of high-magnitude features during inference.

Machine Learning Model Design and Training

The intrusion detection engine integrated into the proposed IDSMS employs a two-stage ensemble machine learning architecture. Stage A performs binary classification to distinguish benign and malicious traffic using a calibrated stacking ensemble composed of Random Forest, Gradient Boosting, and XGBoost classifiers, with Logistic Regression as the meta-classifier. Stage B performs multi-class attack classification using a Random Forest classifier trained exclusively on malicious traffic samples.

The models were trained offline using the CIC-IDS2017 dataset, which contains realistic benign and attack traffic flows represented by 78 numerical flow-based features. Prior to training, feature normalization was applied using standard scaling, and identifier-based fields such as IP addresses and ports were removed to prevent information leakage.

Probability calibration and threshold optimization were applied in Stage A to improve detection reliability under class imbalance. The trained models were then deployed as an inference service and integrated into the proposed system through an API, enabling real-time classification of live network flows.

Machine Learning-Based Intrusion Analysis

Extracted flow features are transmitted to a remote machine learning inference service through a secure API. The detection engine employs supervised learning models trained on labeled flow-based intrusion datasets, enabling classification of traffic into benign or malicious categories.

The inference service outputs a risk level, attack probability, and predicted attack type, consistent with modern IDS frameworks that emphasize probabilistic decision-making rather than binary classification [6], [14], [22]. This decoupled design allows independent updating of detection models without modifying the traffic capture layer.

Data Storage and Logging Mechanism

All analyzed flows and prediction results are stored in a centralized database. Each record includes flow metadata, extracted statistical features, predicted risk classification, probability score, and timestamp. This persistent storage supports forensic analysis, trend evaluation, and system performance assessment.

Figure 3 presents the database schema used by the proposed IDSMS. Captured network flows are stored with their extracted statistical features and corresponding prediction outputs. The schema supports traceability between observed traffic, model decisions, and logged security events, enabling real-time dashboard updates and retrospective forensic analysis. The ER diagram represents the logical data model; implementation may store selected fields in a consolidated logging table to simplify real-time insertion and dashboard querying.

Figure 3. Database Schema of the Proposed IDSMS

Flow-level logging aligns with recent IDS research advocating standardized and structured data storage to improve transparency and reproducibility [4], [12].

Web-Based Visualization and Threat Management

A web-based Intrusion Detection and Security Management System (IDSMS) provides real-time and historical insights into network activity. The dashboard displays key metrics such as total network flows, detected attacks, attack rate, and risk-level distribution. Visual components include time-series graphs, attack distribution charts, and top attacked IP summaries.

Detected threats are presented with associated source IP addresses, destination IPs, protocol types, and attack classifications. Administrative controls enable operators to review, manage, and respond to threats, supporting practical deployment scenarios in public and enterprise networks.

Experimental Deployment Environment

The system is deployed in a virtualized environment using VMware. The Kali Linux monitoring node operates alongside the MikroTik gateway, routers, and client devices generating both benign and simulated attack traffic. This setup ensures that captured flows closely reflect real-world network behavior while allowing controlled experimentation.

Such deployment-focused evaluation addresses a key limitation identified in prior IDS studies, which often lack real-time operational validation [4], [23].

SYSTEM ARCHITECTURE AND DESIGN

Overall System Architecture

The proposed Intrusion Detection and Security Management System (IDSMS) is designed using a modular and layered architecture to support real-time network monitoring, scalable analysis, and centralized security management. The architecture separates traffic acquisition, intrusion analysis, data storage, and visualization into independent components, ensuring flexibility, maintainability, and ease of deployment.

The system operates within a gateway-based network environment where client devices connect through routers and a MikroTik gateway. Traffic generated by client devices is passively observed by a dedicated monitoring node, enabling intrusion detection without disrupting normal network operations.

Figure 4. Network Deployment Topology

Network Layer and Traffic Flow

At the network layer, client devices such as mobile phones, laptops, and public-access terminals generate traffic that traverses downstream routers before passing through the MikroTik gateway. This gateway acts as the central routing point and reflects typical configurations used in small enterprises, internet cafés, and pisonet Wi-Fi services.

The MikroTik router provides IP addressing, network address translation (NAT), and routing functions. Importantly, the IDS does not rely on MikroTik’s internal packet inspection; instead, it observes traffic externally to avoid performance degradation and configuration complexity on the gateway device.

Flow Monitoring and Capture Design

A Kali Linux-based monitoring node is connected to the same local network segment as the MikroTik gateway. This node runs a Python-based flow sniffer that captures packets passively from the designated network interface. The sniffer aggregates packets into bidirectional network flows using a five-tuple identifier composed of source IP address, destination IP address, source port, destination port, and transport protocol.

To ensure accurate detection of client-originated threats, the system supports configurable filtering rules that exclude infrastructure-related traffic, such as router management packets and monitoring host traffic. This design ensures that analysis focuses on user-generated traffic, which is critical in shared-access network environments.

Flow Representation and Feature Layer

Each completed flow is transformed into a structured feature vector representing statistical properties of the communication session. The system extracts approximately 78 flow-level features, including duration metrics, packet and byte counts, packet rates, inter-arrival times, and directional flow statistics.

This feature-based representation abstracts away packet payloads, enabling compatibility with encrypted traffic and reducing privacy concerns. The feature design aligns with established flow-based intrusion detection practices and supports consistent input to the machine learning inference layer.

Machine Learning Inference Integration

The intrusion analysis component is implemented as a remote machine learning inference service accessed through a secure API. Extracted flow features are transmitted from the monitoring node to the inference service, where trained models classify each flow as benign or malicious.

The inference service returns structured outputs including predicted risk level, probability of attack, and attack category. By decoupling traffic capture from model inference, the system allows independent updates to detection models without modifying the monitoring infrastructure. This architectural choice supports scalability and long-term system evolution.

Data Storage and Logging Architecture

All analyzed flows and prediction results are stored in a centralized relational database. Each database record includes flow metadata, extracted features, classification results, and timestamps. Centralized storage enables historical analysis, auditing, and system performance evaluation.

This logging architecture supports both real-time monitoring and retrospective investigation, addressing operational requirements for network administrators and security analysts.

Web-Based Security Management Interface

A web-based dashboard serves as the system’s visualization and management layer. The interface provides real-time summaries of network activity, including total flows processed, detected attacks, and traffic trends. Graphical elements such as charts and tables enable intuitive analysis of security events.

Administrators can inspect individual flow records, review detected threats, and analyze historical patterns. The dashboard is designed to support decision-making rather than automated enforcement during development, allowing administrators to validate detection behavior before enabling response actions.

Figure 5 illustrates the operational workflow of the security analyst or administrator when handling detected intrusion events. After an alert appears on the dashboard, the administrator reviews the event, inspects the corresponding flow details, and decides whether to block the source or ignore the alert. This workflow highlights the role of the proposed system not only as a detection platform but also as a security management and decision-support tool.

IMPLEMENTATION

Development Environment and Tools

The proposed Intrusion Detection and Security Management System (IDSMS) was implemented using a combination of networking hardware, virtualization tools, and open-source software frameworks. A MikroTik router running RouterOS served as the network gateway, while the intrusion monitoring component was deployed on a Kali Linux virtual machine hosted in a VMware environment. This setup enabled controlled experimentation while closely emulating real-world deployment conditions.

Python was selected as the primary programming language for system development due to its extensive support for network analysis, machine learning integration, and rapid prototyping. Supporting tools included packet capture libraries, HTTP communication modules, and database connectors, facilitating seamless interaction between system components.

Flow Sniffer Implementation

The flow monitoring component was implemented as a Python-based sniffer executed through the command-line interface of the Kali Linux environment. Packet capture was performed on a designated network interface connected to the MikroTik gateway. The sniffer passively observes live traffic and aggregates packets into bidirectional flows using a five-tuple identifier consisting of source IP address, destination IP address, source port, destination port, and transport protocol.

To prevent interference from infrastructure traffic, configurable environment variables were used to exclude router and monitoring host IP addresses from analysis. Flow termination was determined using idle timeouts and minimum packet thresholds to ensure that only meaningful traffic sessions were exported for analysis.

Figure 6. Flow Capture and Feature Extraction Pipeline

Feature Extraction and Flow Processing

For each completed flow, the system computes a comprehensive set of statistical features that characterize the behavior of the communication session. These features include flow duration, packet counts, byte counts, packet rates, inter-arrival times, and directional statistics. Feature extraction is performed locally on the monitoring node to minimize data transmission overhead and ensure real-time performance.

Extracted features are formatted into structured data objects compatible with the machine learning inference service. Basic validation checks are applied to ensure feature completeness before transmission.

Machine Learning API Integration

The machine learning inference component was implemented as an external API service. The monitoring node sends extracted flow features to the API using secure HTTP requests. This service processes the input features using trained machine learning models and returns classification results.

Each response includes the predicted traffic label (benign or malicious), attack probability score, and identified attack type when applicable. This API-based integration allows the detection models to be updated or replaced independently from the flow capture logic, supporting extensibility and continuous improvement.

During development, network connectivity constraints were addressed by configuring appropriate routing and interface modes to ensure reliable communication between the monitoring node and the inference service.

Database and Data Management Implementation

A centralized relational database was used to store analyzed flows and prediction results. Each database entry includes flow identifiers, extracted statistical features, prediction outputs, and timestamps. The database schema was designed to support efficient querying for real-time dashboard updates and historical analysis.

Data persistence enables tracking of network behavior over time and supports post-analysis of detected threats. This storage layer plays a critical role in validating detection performance during development and testing.

Web-Based Dashboard Implementation

A web-based security dashboard was developed to provide visualization and management capabilities. The dashboard displays real-time statistics such as total flows processed, detected attacks, attack rates, and risk-level distributions. Interactive tables allow administrators to inspect individual flow records and review detection results.

Figure 7. Threat Reports module of the IDSMS showing summarized statistics and per-flow event records.

The interface was designed with development-stage validation in mind, emphasizing transparency and interpretability rather than automated enforcement. This approach allows system behavior to be closely monitored and verified before enabling active response mechanisms.

Testing and Development Configuration

Testing was conducted using a combination of normal network activities and simulated attack traffic. Generated traffic patterns were used to validate flow capture accuracy, feature extraction correctness, API communication, and database logging. These tests confirmed that the system components operate cohesively under development conditions.

The implementation supports future integration of automated mitigation actions, such as blocking malicious IP addresses through the MikroTik router, although such enforcement mechanisms were not enabled during the development phase.

Overview of Development-Stage Results

This section presents and discusses the results obtained during the development and functional testing phase of the proposed Intrusion Detection and Security Management System (IDSMS). The evaluation focuses on validating system functionality, data flow correctness, and integration performance rather than benchmarking detection accuracy against large-scale real-world datasets.

The network traffic used in this phase consisted of a mixture of benign activities and intentionally generated attack traffic designed to test the system’s capability to capture, analyze, classify, and store flow-level information. The results demonstrate that the system operates as intended across all architectural layers, from live traffic capture to dashboard visualization.

Flow Capture and Traffic Visibility

During testing, the flow sniffer successfully captured live traffic traversing the MikroTik gateway and aggregated packets into bidirectional flows. Each flow was uniquely identified using source IP address, destination IP address, source port, destination port, and protocol.

The system consistently recorded flow metadata such as flow duration, packet count, and byte volume. The presence of multiple distinct source IP addresses in the captured data confirms that the system is capable of differentiating traffic generated by individual client devices. This behavior is essential for deployment in shared-access environments, such as pisonet Wi-Fi services, where multiple users generate concurrent traffic.

The successful extraction of flow-level statistics aligns with findings in flow-based IDS literature, which emphasize the reliability of flow representations for real-time monitoring and anomaly detection [1], [3].

Feature Generation and Statistical Metrics

For each completed flow, the system generated a structured feature vector consisting of approximately 78 statistical attributes. Key computed metrics included flow duration, packets per second, bytes per second, forward and backward packet counts, and inter-arrival time statistics.

The consistency of these metrics across repeated traffic patterns indicates that the feature extraction process is stable and deterministic. During simulated attack scenarios, abnormal traffic behaviors—such as unusually high packet rates or short inter-arrival times—were reflected in elevated flow-level metrics, demonstrating the sensitivity of the feature set to anomalous behavior.

This result supports prior research indicating that statistical flow features are effective descriptors for distinguishing benign and malicious traffic patterns [4], [10].

Machine Learning Inference Results

Extracted flow features were successfully transmitted to the machine learning inference API and processed without data loss. The inference engine returned prediction results including traffic classification (benign or malicious), probability scores, and identified attack types.

During development testing, most flows were classified as benign, while simulated attack traffic produced elevated probability scores and corresponding attack labels. Although these results do not represent real-world attack prevalence, they confirm that the inference pipeline correctly processes input features and returns interpretable outputs.

The probabilistic output format enables nuanced risk assessment rather than rigid binary decisions, which is consistent with modern IDS design principles [6], [14].

Detection Performance of the Integrated Machine Learning Engine

The integrated two-stage ensemble detection engine, which was previously trained and evaluated using the CIC-IDS2017 dataset, achieved strong performance. In the present system, the trained model was integrated and validated at the functional level using simulated attack traffic. Stage A (binary classification) achieved an accuracy of 99.92% with a ROC-AUC score of 0.99987, indicating near-perfect separation between benign and malicious traffic. Stage B (multi-class classification) achieved an overall accuracy of 99.83% across fourteen attack categories.

These results confirm that the machine learning component of the proposed IDSMS is not merely a conceptual module but a validated and high-performing detection engine suitable for real-time deployment. It should be noted that these quantitative performance results were obtained during offline training and evaluation of the detection models, while the present system-level experiments focus on validating real-time integration, data flow correctness, and operational functionality.

CONCLUSION AND FUTURE WORK

Conclusion

This study presented the development and implementation of a real-time, flow-based Intrusion Detection and Security Management System (IDSMS) that integrates live network traffic monitoring, machine learning-based intrusion analysis, centralized data storage, and web-based visualization. Unlike many existing IDS studies that focus primarily on offline datasets and model accuracy, this work emphasized system-level design and operational deployment, demonstrating how flow-based intrusion detection can be implemented in a practical network environment.

The system successfully captured live traffic from a MikroTik-based network, aggregated packets into bidirectional flows, extracted statistical features, and transmitted these features to a machine learning inference service for classification. The results were persistently stored in a database and presented through an interactive dashboard, enabling real-time monitoring and historical analysis. Development-stage testing using simulated attack traffic confirmed that the system components function cohesively and that intrusion events are correctly detected, logged, and visualized.

Overall, the findings validate the feasibility of deploying a modular, flow-based IDS capable of supporting shared-access network environments such as pisonet Wi-Fi services, small enterprises, and IoT-enabled infrastructures. The proposed system provides a solid foundation for real-world intrusion detection by combining research-driven methodologies with practical engineering implementation.

Limitations

Although the system demonstrates correct functionality and integration, the evaluation was conducted under development-stage conditions using simulated attack traffic and a limited number of client devices. As such, the results do not fully represent large-scale operational environments with diverse traffic patterns and real-world attack behaviors. Additionally, automated response mechanisms, such as real-time blocking or quarantine of malicious devices, were intentionally disabled during development to prioritize validation and system stability.

Future Work

Future research and development will focus on extending the system’s capabilities and evaluating its performance under real-world conditions. This includes deployment in shared-access environments similar to those studied in recent Pisonet traffic analyses [25], [26], to validate detection robustness under diverse and dynamic user behaviors. Planned enhancements include large-scale deployment involving multiple client devices and prolonged monitoring periods to assess scalability, detection accuracy, and system robustness. Integrating automated mitigation mechanisms, such as dynamic firewall rule enforcement through the MikroTik router, will enable real-time response to detected threats.

Further work will also explore adaptive and federated learning approaches to continuously improve detection models while preserving data privacy. Expanding the system to support additional network environments, including cloud-based and distributed infrastructures, represents another promising direction. Finally, comprehensive benchmarking against established IDS datasets and comparative evaluation with existing systems will be conducted to quantify performance gains and validate detection effectiveness.

Design and Development of a Real-Time Flow-Based Intrusion Detection and Security Management System Using a Two-Stage Ensemble Model

Jimson A. Olaybar1, Patrick D. Cerna2

1,2College of ICT and Engineering, State University of Northern Negros, Sagay City, Negros Occidental, Philippines

1FCSIT, Southern Leyte State University – Main Campus, Sogod, Southern Leyte, Philippines

[email address omitted]

ABSTRACT

The increasing complexity of modern network environments has heightened the need for practical and scalable intrusion detection solutions. This study presents the development of a real-time, flow-based Intrusion Detection and Security Management System (IDSMS) that integrates live traffic monitoring, machine learning-based intrusion analysis, centralized data storage, and web-based visualization. The system captures network traffic from a MikroTik-based gateway using a passive flow sniffer deployed on a Kali Linux monitoring node. Packets are aggregated into bidirectional flows and transformed into statistical feature vectors, which are analyzed by a machine learning inference service through an application programming interface. Detection results, including risk level and attack classification, are stored in a centralized database and presented through an interactive dashboard. Development-stage testing using simulated attack traffic demonstrates the system's ability to capture, analyze, and visualize network threats in real time. The proposed system provides a practical foundation for deployment in shared-access networks, small enterprises, and IoT-enabled environments.

Keywords — Intrusion Detection System, Flow-Based Analysis, Machine Learning, Network Security, Real-Time Monitoring

1. INTRODUCTION

The rapid growth of networked systems, including enterprise networks, Internet cafés, public Wi-Fi services, and IoT-enabled environments, has significantly increased exposure to cyber threats. Modern attacks such as port scanning, brute-force login attempts, DNS amplification, and distributed denial-of-service (DDoS) attacks continue to evolve in scale and sophistication, making traditional signature-based intrusion detection systems (IDS) insufficient for real-time protection [1], [4].

Recent studies emphasize the effectiveness of flow-based intrusion detection, which analyzes statistical properties of network flows rather than packet payloads. This approach enables efficient monitoring of encrypted traffic while reducing computational overhead, making it suitable for real-time and resource-constrained environments [2], [3], [7]. Machine learning (ML) and deep learning techniques further enhance flow-based IDS by learning complex traffic patterns and improving anomaly detection accuracy [6], [14], [22].

Despite advances in detection models, many existing IDS studies focus primarily on offline datasets and lack full system integration, limiting their applicability in operational networks [4], [10]. Real-world deployment requires not only accurate models but also live traffic capture, scalable inference, centralized logging, and actionable security management interfaces. Furthermore, public-access networks such as pisonet or shared Wi-Fi services demand IDS solutions capable of identifying malicious client devices while preserving normal user traffic. Recent studies have demonstrated the feasibility of anomaly detection and traffic pattern analysis in real-world Pisonet environments using dynamic time warping and seasonal decomposition techniques [25], [26].

To address these challenges, this study presents the development and implementation of a real-time flow-based Intrusion Detection and Security Management System (IDSMS). The proposed system integrates live network traffic capture, flow-level feature extraction, machine learning-based attack classification, and a web-based security management platform. The system is designed to operate with a MikroTik gateway and downstream routers, enabling visibility into client-generated traffic while supporting real-time detection and response.

Unlike dataset-only approaches, this work emphasizes end-to-end system development, demonstrating how flow-based IDS concepts can be operationalized into a working security platform. The system architecture supports live monitoring, historical analysis, and threat management, providing a practical foundation for deployment in small enterprise networks, IoT environments, and public internet access services.

2. OBJECTIVES OF THE STUDY

This study aims to design, develop, and evaluate a comprehensive flow-based intrusion detection system with integrated security management capabilities. Specifically, the objectives are:

To design and implement a real-time flow-based network monitoring system capable of capturing live traffic from a MikroTik gateway environment without disrupting normal network operations.

To develop a machine learning-based intrusion detection engine that utilizes a two-stage ensemble approach for binary classification (benign vs. malicious traffic) and multi-class attack classification.

To create an integrated security management platform featuring centralized data storage, web-based visualization, and real-time threat monitoring capabilities.

To validate the system functionality through development-stage testing using simulated attack traffic and evaluate its operational feasibility for deployment in shared-access network environments.

3. SCOPE OF THE STUDY

This research focuses on the following scope:

Geographical and Institutional Scope: The study is conducted within the network infrastructure of the State University of Northern Negros, Philippines, with applicability to similar educational institutions and small-to-medium enterprise environments.

Technical Scope:

Network environment: MikroTik router-based gateway with downstream routers

Monitoring platform: Kali Linux virtual machine

Detection approach: Flow-based analysis using statistical features

Machine learning framework: Two-stage ensemble model

System integration: Python-based implementation with web dashboard

Temporal Scope: The development and testing phase was conducted during the 2024-2025 academic year, with system validation performed under controlled laboratory conditions.

Functional Scope: The system includes live traffic capture, flow aggregation, feature extraction, machine learning inference, database logging, and web-based visualization components. Automated mitigation actions are excluded from the current implementation.

Limitation Scope: Evaluation is limited to development-stage testing with simulated attack traffic; large-scale real-world deployment and performance benchmarking are designated as future work.

This research holds significant value for multiple stakeholders in the cybersecurity and network management domains:

4.1 For Educational Institutions

The system provides a cost-effective intrusion detection solution for universities and colleges with limited cybersecurity budgets, particularly relevant for Philippine higher education institutions facing resource constraints.

4.2 For Network Administrators

5. RELATED STUDIES

5.1 Flow-Based Intrusion Detection Foundations

Flow-based intrusion detection has emerged as a scalable alternative to payload inspection, particularly for monitoring encrypted traffic. Satheesh et al. [1] demonstrated early integration of flow-based anomaly detection with SDN/OpenFlow environments, establishing the feasibility of flow-driven security monitoring in programmable networks. Pontes et al. [2] introduced a novel detection method using the inverse Potts model, showing that flow representations can capture complex network behaviors beyond traditional feature engineering. For wireless environments, Segura-Garcia et al. [3] developed HeaderHunter, a real-time flow-based IDS for IEEE 802.11 networks, validating the practicality of flow-level monitoring in wireless systems.

5.2 Standardization and Dataset Development

A persistent challenge in flow-based IDS research is feature definition inconsistency and dataset variability. Sarhan et al. [4] emphasized the need for standardized feature sets, noting that differences in extraction and labeling procedures limit reproducibility. Several datasets have been developed to address these issues, including Edge-IIoTset by Ferrag et al. [5] for IoT/IIoT scenarios and the widely adopted CICIDS2017 dataset used in benchmarking studies by Kurniabudi et al. [10] and Maseer et al. [11]. Komisarek and Pawlicki [12] further contributed a refined dataset specifically designed for real-time NIDS settings.

5.3 Machine Learning Integration in IDS

Deep learning approaches have gained prominence for their ability to model complex traffic patterns. Vishwakarma and Kesswani [6] proposed a deep neural network-based real-time IDS for IoT, reporting improved detection performance in constrained environments. Rathore et al. [7] and Fraihat et al. [8] explored flow-driven deep learning models for IoT anomaly detection, while Manocchio et al. [20] introduced FlowTransformer, an attention-based model for learning temporal dependencies within flow records.

5.4 Federated Learning for Distributed Detection

Federated learning has emerged as a privacy-preserving approach for distributed intrusion detection. de Oliveira et al. [13] presented F-NIDS, demonstrating federated intrusion detection without centralized data collection. Doriguzzi-Corin and Siracusa [21] proposed FLAD for adaptive DDoS detection, while Nugraha et al. [22] investigated federated learning with variational autoencoders for anomaly detection.

5.5 Enhancement Techniques and Practical Applications

Several studies have focused on improving IDS reliability through techniques like data augmentation and feature encoding. Mohammad et al. [14] explored deep learning combined with data augmentation, while Alitbi et al. [15] proposed incremental feature encoding for real-time constraints. Recent work has extended flow-based analysis to practical scenarios, including Pisonet traffic analysis [25] and dynamic network visualization [26], highlighting the growing relevance of operational deployment considerations.

5.6 Research Gap Addressed by This Study

While extensive research exists on flow-based IDS models and algorithms, few studies address comprehensive system integration and operational deployment. Most existing work focuses on offline evaluation using datasets, with limited emphasis on end-to-end system implementation. This study addresses this gap by developing a complete Intrusion Detection and Security Management System (IDSMS) that integrates live traffic capture, machine learning inference, centralized storage, and web-based management interfaces.

6. METHODOLOGY

6.1 System Architecture Overview

The proposed IDSMS follows a modular architecture with five primary components: (1) live traffic capture from client devices through router and MikroTik gateway infrastructure, (2) flow aggregation and feature extraction by a dedicated monitoring node, (3) machine learning-based intrusion analysis through an inference service, (4) centralized data storage in a relational database, and (5) web-based visualization and threat management via an interactive dashboard. The system operates within a gateway-based network environment where client traffic passes through routers and a MikroTik gateway, with a dedicated monitoring node performing passive traffic observation and feature extraction before analysis results are stored and visualized.

Figure 1. Overall System Architecture Diagram

6.2 Live Traffic Capture and Flow Aggregation

The traffic processing pipeline, illustrated in Figure 2, begins with packet capture using a Python-based flow sniffer on a Kali Linux VM. The system performs flow aggregation by grouping packets into bidirectional flows based on five-tuple identifiers (source/destination IP/port + protocol). Upon flow completion, feature extraction generates approximately 78 statistical attributes per flow. These feature vectors are sent via REST API to a machine learning inference service, which returns JSON-formatted classification results (e.g., {'data': value, 'risk_level': 'high', 'attack_type': 'DDoS'}). Idle timeout mechanisms ensure timely flow termination and feature export.

Figure 2. Flow Capture and Feature Extraction Pipeline

6.3 Feature Extraction and Preprocessing

For each completed flow, the system extracts approximately 78 statistical features capturing temporal, volumetric, and directional characteristics. These include flow duration, packet counts, byte rates, inter-arrival times, and forward-backward packet statistics. Following feature extraction, the data undergoes JSON formatting to create structured API payloads. These formatted feature vectors are transmitted to the ML inference API, which performs real-time classification and returns prediction results (including risk level, attack probability, and classification labels). All results are then stored in the centralized database and made available for visualization through the web dashboard. Feature normalization is applied to ensure compatibility with machine learning models, and filtering removes incomplete or insignificant traffic. This complete runtime processing pipeline from packet aggregation through database storage to dashboard visualization is shown in Figure 3.

Figure 3. Runtime Data Processing Pipeline of the Proposed IDSMS

6.4 Machine Learning Model Design and Training

6.4.1 Two-Stage Ensemble Architecture

The intrusion detection engine employs a two-stage ensemble approach:

Stage A: Binary classification (benign vs. malicious) using a calibrated stacking ensemble of Random Forest, Gradient Boosting, and XGBoost classifiers with Logistic Regression as meta-classifier

Stage B: Multi-class attack classification using a Random Forest classifier trained exclusively on malicious samples

6.4.2 Training Process

Models were trained offline using the CIC-IDS2017 dataset with 78 numerical flow-based features. Preprocessing included feature normalization using standard scaling and removal of identifier-based fields (IP addresses, ports) to prevent information leakage. Probability calibration and threshold optimization were applied in Stage A to address class imbalance.

6.5 Machine Learning Inference Integration

Extracted flow features are transmitted to a remote inference service via secure API. The service returns structured outputs including risk level, attack probability, and attack classification. This decoupled design enables independent model updates without modifying the traffic capture infrastructure.

6.6 Data Storage and Logging

A centralized relational database implements the storage layer with a normalized schema consisting of five primary tables: Flows (flow metadata), Features (extracted attributes), Users (access control), Predictions (classification outputs), and Attacks (threat records). This structure ensures comprehensive logging of all processed traffic while supporting efficient queries for both real-time monitoring and historical forensic analysis, as detailed in Figure 4.

Figure 4. Database Schema of the Proposed IDSMS

6.7 Web-Based Security Management Interface

A web dashboard provides visualization and management capabilities, displaying metrics such as total flows processed, detected attacks, attack rates, and risk-level distributions. The interface includes time-series graphs, attack distribution charts, and interactive tables for detailed flow inspection. The dashboard supports an interactive security analyst workflow where: (1) an alert appears in the interface, (2) the admin reviews the alert details, (3) checks flow-specific information, (4) decides on an action, and (5) selects either to block the malicious traffic or ignore the alert. This decision-making process is illustrated in Figure 5.

Figure 5. Security Analyst/Admin Decision-Making Workflow

6.8 Experimental Deployment Environment

The system was deployed in a virtualized VMware environment with the following network topology: client devices (1) connect to a router (2), which forwards traffic through a MikroTik gateway (3) linked to an ISP for external access. A dedicated Kali Linux sniffer node is positioned to monitor traffic via a switch/LAN connection, enabling passive observation of all network activity. This setup facilitates controlled experimentation while emulating real-world network behavior, as illustrated in Figure 6.

Introduction

The increasing complexity and frequency of cyber threats have made Intrusion Detection Systems (IDS) a critical component in ensuring network security. Traditional signature-based IDS often fail to detect new or evolving attacks, particularly zero-day exploits, due to their reliance on predefined patterns (Buczak & Guven, 2016). To overcome these limitations, researchers have turned toward machine learning-based anomaly detection techniques capable of recognizing novel attack behaviors (Sommer & Paxson, 2010). However, many existing machine learning approaches struggle with class imbalance, probability miscalibration, and threshold optimization, which can lead to unreliable detection in real-world environments (Niculescu-Mizil & Caruana, 2005; Zadrozny & Elkan, 2002).

Benchmark datasets have played a crucial role in evaluating IDS performance. Early datasets such as KDD CUP 99 (Tavallaee et al., 2009) and UNSW-NB15 (Moustafa & Slay, 2015) were instrumental but limited by redundancy and outdated attack types. The CIC-IDS2017 dataset (Sharafaldin et al., 2018) addressed these shortcomings by providing realistic traffic with modern attack profiles, including DoS, DDoS, and PortScan, among others (Ring et al., 2019).

Ensemble learning techniques, including Random Forest (Breiman, 2001), Gradient Boosting (Friedman, 2001), and XGBoost (Chen & Guestrin, 2016), have demonstrated strong performance in IDS applications by combining multiple classifiers to reduce bias and variance. Studies by Kevric et al. (2017) and Aljawarneh et al. (2018) showed that combining tree-based models can improve detection rates, while Almseidin et al. (2017) highlighted the superior accuracy of ensemble methods compared to single classifiers.

Building upon these insights, this study proposes a two-stage ensemble learning model designed to improve both binary detection and multi-class attack classification through calibrated stacking and optimized threshold tuning. This model aims to achieve higher detection accuracy and robustness against imbalanced network traffic, thereby addressing key limitations in existing IDS frameworks.

Objectives of the Study

This study aims to develop and evaluate a two-stage ensemble-based Intrusion Detection System (IDS) capable of improving detection accuracy, probability calibration, and attack categorization performance. Specifically, the objectives are to:

Design a two-stage IDS framework where Stage A performs binary classification (benign vs. attack) and Stage B performs multi-class classification (specific attack types).

Implement a calibrated stacking ensemble integrating Random Forest, Gradient Boosting, and XGBoost classifiers for reliable probability estimation.

Conduct a comprehensive performance evaluation using the CIC-IDS2017 dataset, focusing on metrics such as precision, recall, F1-score, and ROC-AUC.

Compare the proposed approach with existing IDS models to demonstrate its effectiveness and efficiency in real-world cybersecurity environments.

Materials and Methods

Dataset and Preprocessing

We utilized the CIC-IDS2017 dataset (Sharafaldin et al., 2018), which contains realistic network traffic with both benign and attack flows. The dataset includes 2.8 million samples across 80 features, capturing various attack scenarios over multiple days. Following the dataset characterization by Sharafaldin et al. (2018), we focused on network-layer attacks detectable through flow statistics. Haider et al. (2017) discussed the importance of realistic dataset generation using fuzzy qualitative modeling, which aligns with our use of the CIC-IDS2017 dataset to ensure real-world applicability.

Figure 1. Dataset distribution across traffic types for training and testing sets (CIC-IDS2017)

Data preprocessing involved several steps. First, we normalized column names and handled missing values by replacing them with zeros. Numerical features were standardized using StandardScaler, while non-numeric identifiers were excluded to prevent data leakage. The label column was processed using Unicode normalization to ensure consistency across different attack naming conventions.

Feature Selection

Based on the analysis by Garcia et al. (2014), we selected 78 numerical features representing network flow characteristics. Features related to pure identifiers (IP addresses, ports, timestamps) were excluded, while behavioral features like flow bytes per second, packets per second, and inter-arrival times were retained. This approach aligns with feature selection strategies discussed by Aljawarneh et al. (2018) for handling high-dimensional network data.

Model Architecture

Stage A: Binary Classification (Benign vs Attack)

We implemented a stacking ensemble combining Random Forests (Breiman, 2001), Gradient Boosting (Friedman, 2001), and XGBoost (Chen & Guestrin, 2016). The ensemble employs logistic regression as a meta-classifier, following the stacked generalization framework (Wolpert, 1992). To address probability calibration, we incorporated CalibratedClassifierCV with sigmoid calibration (Niculescu-Mizil & Caruana, 2005; Platt, 1999), which has shown effectiveness in cybersecurity applications (Zadrozny & Elkan, 2001).

Conclusion and Recommendation

This study proposed a two-stage ensemble learning framework for network intrusion detection, designed to improve both detection accuracy and classification reliability. By combining calibrated stacking ensembles in Stage A and Random Forest-based multi-class classification in Stage B, the model effectively separated benign from malicious traffic and accurately identified specific attack types. Evaluation using the CIC-IDS2017 dataset demonstrated state-of-the-art performance, achieving 99.92% binary accuracy and 99.83% multi-class accuracy across 14 attack categories.

The success of the proposed model can be attributed to three main factors: (1) the separation of binary and multi-class tasks, which reduced class interference; (2) the implementation of probability calibration and threshold optimization, enhancing decision reliability; and (3) the integration of ensemble-based methods, which reduced overfitting and improved generalization. Comparative analysis with existing intrusion detection models confirmed that the proposed approach outperformed recent ensemble and deep learning methods in terms of accuracy, recall, and computational efficiency.

For future research, the following directions are recommended:

Integration of Payload Features: Extend the model to detect web-based and application-layer attacks through deep packet inspection and content-aware features.

Adaptive and Online Learning: Incorporate incremental learning mechanisms to enable continuous adaptation to evolving attack behaviors and zero-day threats.

Deployment Optimization: Investigate model compression and lightweight ensemble configurations to ensure efficient deployment in resource-constrained environments, such as IoT and edge devices.

Cross-Domain Evaluation: Test the framework on alternative datasets and real network traffic to assess generalization across different cybersecurity contexts.

Although the proposed two-stage ensemble model achieved high accuracy and robustness, several limitations must be acknowledged. First, the experiments were conducted solely on the CIC-IDS2017 dataset, which, despite its realism, may not fully represent emerging or application-layer attack patterns. Second, the study focused primarily on network-layer traffic and did not incorporate payload-based or encrypted flow features. Finally, computational resource requirements may limit the scalability of the model in large-scale or real-time environments without optimization. These limitations will guide the direction of future work.
